## 0. 역할 분담 (변하지 않는 전제)

- **Claude**: 구현·문서·검증·보고. **커밋/머지/push 하지 않는다.**
- **Codex**: 리뷰·커밋 판단·마이그레이션/스키마 변경 승인.
- **사용자**: 비개발자 사장님. 최종 방향 결정. 설명은 항상 쉬운 말로.

## 1. 작업 시작 전 (매 세션)

1. `cd "D:/Documents/ERP-1"` — cwd는 매 명령 후 리셋되므로 git/npm 전 항상 이동.
2. `git status` — **기존 미커밋 변경을 확인하고 절대 건드리지 않는다.** 남의(이전 세션·Codex) 작업 위에 덮어쓰지 않는다.
3. 현재 위치 파악: `docs/order-moa-progress-data.json`(진행 단일 소스) + `docs/NEXT-SESSION.md`(있으면).
4. **구현 전 관련 문서·코드를 실제로 읽는다.** 헌장·모듈맵에서 해당 모듈 찾기 → 관련 spec → 관련 코드. 기억이나 요약만으로 코드를 고치지 않는다.
5. 작업에 차수 딱지를 붙인다(1차/1.5차/2차/3차/제외). 2차 이상이면 구현하지 않고 사용자에게 차수 확인.

## 2. 구현 중

- **좁은 MVP 우선.** 요청 범위만. "이왕 하는 김에"는 [나중] 목록으로.
- 새 로직은 **순수 함수로 분리**하고 단위 테스트를 같이 만든다(파서·합산·payload 빌더가 선례). UI 파일에 계산 로직을 심지 않는다.
- 기존 패턴 재사용: 타입은 `lib/domain/types`, DB 접근은 `order-store.ts` 스타일, 화면은 기존 뷰 구조.
- DB 불변 규칙(헌장 §3)을 위반하는 코드는 쓰지 않는다 — amount insert 금지, 단가 재조회 금지, 하드 delete 금지.
- **마이그레이션·스키마 변경의 적용/커밋은 Codex 승인 전 하지 않는다.** SQL 초안 작성은 사용자가 명시 지시하거나 Codex가 범위를 승인한 단위에서만 한다.
- 새 의존성 추가는 최후 수단 — 몇 줄이면 되는 것에 패키지를 넣지 않는다.

## 3. 작업 후 검증 (한 세트 — 코드 변경 시 필수)

```
cd "D:/Documents/ERP-1"        # 루트
npm test                        # 5/5
cd web
npm test                        # 전건 (현재 78/78)
npm run build                   # 성공
npm audit --audit-level=low     # 0건
```

- UI 변경 시: 브라우저 확인까지(dev 서버 응답 + 해당 화면 동작). **로직 테스트 통과만으로 "고쳐졌다" 선언 금지** — 시각 확인이 안 되면 "코드상 수정, 화면 미확인"으로 보고.
- 모바일 영향 시 390px, 명세서 변경 시 인쇄 미리보기, DB 경로 변경 시 RLS A/B 시나리오.
- 파서 변경 시 실제 발주 fixture 갱신·통과.
- 검증을 위해 `.env.local`을 옮겼으면 원위치 복원 + git 미추적 재확인.
- **디버깅과 리뷰는 한 세트**: 증상→원인→수정→검증 결과를 묶어서 기록. 원인 모르는 수정은 하지 않는다.

## 4. 기록 (작업이 끝나면)

1. `docs/agent-worklog.md`에 추가 — 형식: `## YYYY-MM-DD 주체 (제목)` + 목적/변경/검증/다음.
2. 진행 상태가 바뀌었으면 `docs/order-moa-progress-data.json` 갱신 → HTML/XLSX 재생성(JSON이 단일 소스, 3종 불일치 금지).
3. 커밋하지 않는다. 변경 파일 목록을 보고에 남겨 Codex가 판단하게 한다.

## 5. 보고 형식 (사용자에게)

- **비개발자 기준**: "RLS 정책을 우회하는 42501" 대신 "다른 회사 데이터에 손대면 DB가 거부하는 것을 확인했습니다".
- 파일 경로는 전체 경로로.
- 항상 3분류를 포함:
  - **[개선 아이디어]** — 이번에 안 했지만 가치 있는 것
  - **[위험]** — 남아 있는 구멍·전제
  - **[나중]** — 의도적으로 미룬 것과 미룬 이유
- 실패·미완은 그대로 보고한다. 테스트가 깨졌으면 깨졌다고, 실측을 못 했으면 못 했다고. 완료 위장 금지.

## 6. 민감정보·보호 (위반 즉시 중단 사항)

- `.env.local`·Supabase 키·service role key: 출력·커밋·로그 금지. service role key는 클라이언트 코드에 절대 등장 금지.
- 원본 사업자 데이터(태백식품 엑셀 등 실거래처명·전화·사업자번호·매출): 커밋 금지, 문서/샘플에는 가명만.
- 공유 Supabase 프로젝트: `ordermoa_` 접두사 없는 객체 생성 금지, yangsan 객체 조회·수정 금지.

## 7. 확장 요구가 들어왔을 때

1. 헌장 §4 차수 경계표에서 위치 확인.
2. 제외 목록(OCR·카톡 자동·이카운트·직접 발행 등)이면: 만들지 않고 이유를 설명.
3. 2차 이상이면: 구현 대신 로드맵 위치를 안내하고, 정말 앞당길지 사용자에게 확인.
4. 1차 범위면: 진행하되 사이드바에 2차 메뉴를 미리 추가하지 않는다.

## 8. Codex 검수 전제

- Claude의 모든 산출물(코드·문서)은 Codex 검수 대상이다. 보고에 "Codex가 봐야 할 포인트"를 명시한다.
- 스키마·마이그레이션·커밋·머지·push·배포 = Codex 게이트.
- Codex 리뷰 피드백은 맹목 수용도 맹목 방어도 하지 않는다 — 코드로 확인 후 반영/반론.
