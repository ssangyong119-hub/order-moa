## 1. 문서 목적

- 이 문서는 오더모아 **웹 MVP의 개발 기준을 확정**하기 위한 요구사항정의서다.
- **1차 목적:** 무엇을 만들고 무엇을 만들지 않을지(범위)를 확정한다.
- **2차 목적:** 이후 Claude/Codex 협업 개발에서 작업 지시·리뷰의 **기준 문서**로 사용한다.
- 이 문서 다음 산출물은 **기능정의서**이며, 본 문서의 기능 요구사항을 화면·동작·데이터 단위로 구체화한다.

## 2. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 제품명 | **오더모아** (내부 가칭 — 동일 법인명 검색됨, 외부 공개 전 KIPRIS 상표/도메인/앱 이름 중복 확인 필요) |
| 한 문장 정의 | 식당·소매 거래처에서 카톡/문자/전화/사진으로 흩어져 들어온 발주를 취합해, 거래처별 주문표·품목별 총 발주표·단가·거래명세서까지 이어주는 **중간 납품업자 전용 웹 ERP** |
| 대상 사용자 | 식당·카페·반찬가게·마트 등에 식자재/공산품을 반복 납품하는 **중간 도소매업자** |
| 사용자의 업무 위치 | 단순 판매자가 아니라 **거래처 발주 ↔ 도매상 발주 ↔ 납품/명세서/정산**을 잇는 중간 정리자 |
| 기존 ERP와의 관계 | 이카운트 등 범용 ERP(월 4만 원대, 기능의 약 1/10만 사용)를 **전면 대체하지 않는다.** 발주 취합·합산 등 ERP 입력 *이전 단계*의 수작업을 줄이는 보조부터 시작 |

**제품 방향(명시):** 완성형 범용 ERP를 만들지 않는다. **중간 납품업자의 반복 업무를 좁고 깊게** 해결한다. 최종 목표는 "이카운트의 넓은 기능 중 일부만 쓰는 사용자라면 오더모아만으로 핵심 업무가 돌아가는 업종 특화 웹 ERP"다.

## 3. 문제 정의

근거: `erp-discovery-log.md`(친구 통화·이카운트 조사), `order-moa-product-definition.md`, `survey-analysis-2026-06-06.md`.

| # | 핵심 문제 | 근거 강도 |
|---|---|---|
| P1 | 카카오톡·문자·전화·사진 주문이 여러 채널로 **흩어진다** | 강함 (설문: 카톡 개인 4 / 문자 4 / 카톡 단체 3 / 전화 2) |
| P2 | 발주 내용을 ERP·엑셀·장부에 **다시 입력**해야 한다 | 강함 (설문: 매일 옮겨 적음 3건, 통화 메모 일치) |
| P3 | 거래처별 **단가가 다르고 자주 바뀐다** (단가 실수 위험) | 중강 (설문: 단가 변경 잦음 3건, "믿을 수 없는/불투명한 단가") |
| P4 | 여러 거래처 주문의 **상품별 총 물량 합산**이 번거롭다 | 중간 (설문: 합산 번거로움 3건, 통화 메모 일치) |
| P5 | 거래명세서·미수금·입금·세금계산서 정리가 **분리·반복** 관리된다 | 중간 (설문: 미수금 통장 직접확인 3건, 세무 자유응답) |
| P6 | 기존 ERP는 기능이 많지만 **실제 쓰는 기능은 일부**에 집중(발주 수집/정리는 약함) | 중간 (통화: 기능의 약 1/10 사용, 이카운트 조사) |

**가장 강한 단일 신호:** "카톡 및 문자 발주 자동 취합" (설문 1순위 + 자유응답 반복).

## 4. 사용자 유형

| 구분 | 사용자 | 설명 | MVP 1차 대상 |
|---|---|---|---|
| 주 사용자 | 중간 도소매업자 | 식당/마트/카페 등에 납품하는 사장. 발주 취합~명세서까지 직접 처리 | ✅ |
| 확장 사용자 | 업종별 유통업자 | 농산물·축산·수산·공산품·식자재 유통 | 🔶 구조상 허용, 별도 검증 |
| 보조 사용자 | 직원/배송·출고 담당자 | 발주 확인·출고표 조회 등 제한된 작업 | ⛔ (권한 구조만 설계, 기능은 2차) |
| 후순위 사용자 | 거래처(주문자) | 거래처용 주문 링크로 직접 주문 | ⛔ 후순위 후보 (행동 변화 강요 리스크) |

> 원칙(`order-moa-product-definition.md` §10): 거래처의 행동 변화를 처음부터 강요하지 않는다. MVP 1차는 **주 사용자 1인** 사용을 기준으로 설계한다.

## 5. MVP 목표

**핵심 문장:**

> "카톡/문자 발주를 붙여넣으면 거래처별 주문표와 품목별 총 발주표가 만들어지고, 단가와 거래명세서까지 이어지는 중간 납품업자 전용 웹 ERP"

목표는 완성도 높은 ERP가 아니라, **설문에서 가장 강하게 확인된 문제(발주 취합)를 실제 사용자에게 검증**하는 것이다.

## 6. MVP 성공 기준

| 구분 | 기준 |
|---|---|
| 정량 | 샘플 발주 **10건 이상**을 입력해 거래처별 주문표를 만들 수 있다 |
| 정량 | 품목별 총 발주표가 **자동 생성**된다 |
| 정량 | 거래처별 단가가 **자동 적용**된다 |
| 정량 | 사용자가 파싱 결과를 **직접 수정**할 수 있다 |
| 정성 | 실제 납품업자 **1~2명**이 자기 발주 예시로 테스트한다 |
| 정성 | "**다시 써볼 만하다**"는 피드백을 받는다 |
| 정성(가설) | 발주 취합 시간이 기존보다 줄었다고 느낀다 |

**실패 신호(검증 필요):** 카톡 붙여넣기조차 번거롭다 / 거래처·품목·단가 초기 등록이 너무 오래 걸려 포기 / 거래명세서·미수금 없이는 의미 없다고 판단.

## 10. 업무 흐름

**A. 초기 설정 흐름**
1. 로그인 → 회사 생성 → 거래처 등록 → 품목 등록 → 품목 별칭 등록 → 거래처별 단가 등록.

**B. 매일 발주 입력 흐름**
1. 거래처 카톡/문자 발주를 복사 → 붙여넣기(F7) → 규칙 기반 파싱(F8) → 품목 별칭 매칭.

**C. 주문 확인/수정 흐름**
1. 파싱 결과를 표로 표시 → 사람이 품목/수량/단위/단가 확인·수정(F9) → 거래처별 주문 저장(F10).

**D. 품목별 합산표 확인 흐름**
1. 저장된 여러 주문을 품목별로 합산(F11) → 도매상 발주용 총 물량 확인 → 필요 시 CSV 내보내기.

**E. 거래명세서 생성 흐름**
1. 거래처별 주문 선택 → 단가 적용 → 거래명세서 미리보기(F13) → (단순) 인쇄/다운로드.

**F. 월말 정산 후보 흐름 (후순위)**
1. 거래처별 월 매출 합계 → 미수금/입금 수동 체크 → 세금계산서 발행 금액 부족/초과 정리(2차).

## 11. 권한/보안 요구사항

| 항목 | 요구사항 |
|---|---|
| 역할 | `owner`(전체) / `staff`(발주·거래처·품목 입력). **MVP 1차는 owner만 구현**, 스키마는 `company_members.role`로 확장 가능하게 둔다 |
| 회사 단위 접근 제한 | 모든 쿼리는 `company_id` 기준. RLS로 `auth.uid()`의 소속 회사만 접근 |

| 첨부파일/OCR | **후순위** — MVP 1차 업로드 UI 없음 |
| 민감정보 | 최소 저장. 거래처명/전화/사업자번호/단가/미수금/명세서는 민감정보로 취급 |
| 원본 카톡/문자 전문 | **확정**: `order_imports.raw_text`에 저장 가능(파싱 검수 보조), 민감정보 가능→사용자 삭제 제공, 장기보관 후순위. 첨부/OCR 원본은 1차 제외 |
| 환경변수/키 | `.env` 커밋 금지, service role key 클라이언트 노출 금지 |

## 13. 수익화 가설

> 모두 **가설**이며 표본 5건 기준이다. 실사용 테스트로 검증 필요.

| 가설 | 근거 |
|---|---|
| 월 3만~5만 원 지불 가능성 있음 | 설문 지불의사: ≤1만(1)/1~3만(1)/3~5만(1)/5~10만(1)/기능 봐야 판단(1) |
| 기존 ERP **보조 도구**로 시작 가능 | 응답자 전원 ERP 사용 중 → 대체보다 보완 진입이 현실적 |
| **발주 취합 + 미수금/입금**이 유료 전환 핵심 후보 | 1순위 발주 취합, 자유응답 "입금확인·미수금 정리", "품목별 마진 계산기" |
| MVP 실사용 테스트 필수 | "기능을 봐야 판단" 응답 존재 → 화면 없이는 지불 판단 불가 |

## 14. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 사용자가 품목/단가 초기 등록을 귀찮아함 | 샘플 템플릿/엑셀 업로드(후순위), 자주 쓰는 품목부터 유도 |

| 데이터 손실/오입력 | 내보내기 제공, 삭제 전 확인, soft delete 검토 |
