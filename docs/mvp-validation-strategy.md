# 오더모아 영업/검증용 MVP 전략

작성일: 2026-06-29
작성 주체: Claude (제품/검증 전략)
근거 문서: `docs/requirements-definition.md`, `docs/function-specification.md`, `docs/mvp-acceptance-checklist.md`, `docs/db-schema-definition.md`, `docs/supabase-rls-policy.md`, `docs/survey-analysis-2026-06-06.md`, `docs/order-moa-product-definition.md`

> **문서 목적**: 오더모아는 개발자가 매일 쓰는 내부 도구가 아니라, **실제 납품업자에게 보여주고 테스트받아야 하는 업무 도구**다. 따라서 1차 MVP의 목표를 "완성형 ERP"가 아니라 **"실제 납품업자가 자기 발주로 테스트해보고 싶게 만드는 영업/검증용 MVP"**로 재정의한다.
>
> 전제: 수요 근거인 설문은 **5건**으로 작다. 본 문서의 수요·전환 판단은 가설이며, 실사용 테스트로 검증한다.

---

## 1. 현재 가장 큰 리스크

| # | 리스크 | 의미 |
|---|---|---|
| R1 | **개발자가 직접 사용자가 아니다** | 우리는 납품 현장을 매일 겪지 않음 → 진짜 불편을 추측에 의존 |
| R2 | **실제 거래처/품목/단가 데이터가 충분치 않다** | 화면은 만들어도 "넣어볼 데이터"가 없음 |
| R3 | **사용자가 초기 데이터 입력을 귀찮아한다** | 거래처·품목·단가 등록 부담이 첫 사용 장벽 |
| R4 | **기존 ERP 사용자가 옮길 이유가 약하다** | 응답자 전원 ERP 사용 중(이카운트 3) → 대체 동기 약함 |
| R5 | **설문 표본이 5건으로 작다** | 방향 신호일 뿐, 통계 확정 아님 |

→ 결론: "완성도"가 아니라 **"입력 장벽을 우리가 제거한 상태에서 핵심 가치를 체감시키는 것"**이 1차 과제다.

---

## 2. MVP 목표 재정의

| 구분 | 내용 |
|---|---|
| 기존 | 실제 납품업자가 바로 운영 가능한 웹 ERP |
| **조정** | 납품업자에게 **보여주고, 자기 카톡/문자 발주 예시로 테스트받는 영업/검증용 MVP** |

**핵심 문장:**

> "사장님이 평소 카톡/문자로 받은 발주를 붙여넣었을 때, 거래처별 주문표와 품목별 합산표가 바로 나와서 '이거 편한데?'를 느끼게 하는 것"

즉 1차 성공은 "가입자 수"가 아니라 **"테스트한 사장님이 다시 써보고 싶다고 말하는가"**다.

---

## 3. 검증해야 할 질문

- [ ] **카톡/문자 발주 붙여넣기가 실제로 편한가?** (핵심 가설)
- [ ] **카톡 원문을 넣고 거래명세서까지 가는 과정이 불편하지 않은가?** (전체 흐름 가설)
- [ ] **거래처별 단가 관리가 이카운트보다 쉬운가?** (단가 관리 가설)
- [ ] **예상 마진이 보이면 돈 낼 가치가 커지는가?** (마진 표시 가설)
- [ ] 거래처/품목/단가 초기 등록을 감수할 가치가 있는가?
- [ ] **우리가 초기 세팅을 대신해주면** 쓸 의사가 생기는가?
- [ ] 이카운트 등 기존 ERP를 보조하거나 일부 대체할 수 있는가?
- [ ] 월 **3만~5만 원**을 낼 만한 문제가 맞는가?

---

## 4. 초기 세팅 대행 전략

1차 판매/검증에서는 **사용자가 직접 모든 데이터를 넣게 하지 않는다.** 우리가 거래처/품목/단가를 **대신 세팅**해주는 전제로 검증한다(R3 제거).

최소 세팅 데이터:

| 항목 | 분량 |
|---|---|
| 거래처 | 3~5곳 |
| 품목 | 20~50개 |
| 거래처별 자주 쓰는 단가 | 위 거래처×품목 |
| 실제 카톡/문자 발주 예시 | 5~10건 |

→ 사용자는 **"발주 붙여넣기 → 확인/수정 → 합산표 보기"** 만 경험한다. 등록 노동은 우리가 흡수한다.

---

## 5. 데모 데이터 전략

- 실제 데이터가 없을 때도 즉시 보여줄 수 있게 **샘플 데이터**를 준비한다(기능정의서 F: 샘플 데이터 생성).
- 기준 업종: **식자재 납품업**.
- 포함: 거래처 · 품목 · 품목 별칭 · 거래처별 단가 · 발주 예시.
- **개인정보/실제 거래처명은 가명 처리**한다. 전화/사업자번호 등 실제 민감정보는 넣지 않는다(`00` 자리표시자).

데모 데이터 형태 예시(가명):

| 종류 | 예시(가명) |
|---|---|
| 거래처 | 가람식당, 행복마트, 으뜸반찬, 한빛카페 |
| 품목/별칭 | 콩나물(콩,콩나물박스) · 두부(두부판) · 미나리 · 깐양파(양파) · 식탁보 |
| 단가 | 거래처별 상이(예: 콩나물 가람식당 8,000 / 행복마트 7,500) |
| 발주 예시 | "콩나물 2박스\n두부 3판\n미나리 5단" 등 정형/비정형 혼합 |

> 데모 데이터는 시연·화면 검증용이며, 실제 사용자 테스트 시엔 그 사장님의 실제 발주 예시로 교체한다.

---

## 6. 첫 사용자 테스트 절차

1. 사장님에게 **평소 발주 방식** 설명 듣기(채널/건수/번거로운 점)
2. **카톡/문자 발주 예시 확보**(민감정보 가린 캡처 또는 텍스트)
3. 거래처/품목/단가 **최소 세팅(우리가 대행)**
4. 오더모아에서 **발주 붙여넣기 시연**
5. **품목별 합산표** 확인(도매상 발주용)
6. **거래명세서 미리보기** 확인
7. **불편한 점** 질문(어디서 막히는지)
8. **다시 쓸 의향 / 가격** 질문

> 각 단계에서 "막힌 지점·표정·요청"을 기록한다. 정량 지표보다 "다시 쓰고 싶다"는 반응이 1차 판단 기준.

---

## 7. 영업/인터뷰 멘트 초안

- "사장님, **이카운트를 바꾸자는 게 아니라** 카톡 발주 정리만 먼저 줄여보려는 겁니다."
- "**거래처/품목 세팅은 제가 먼저 해드릴게요.** 사장님은 발주만 붙여넣어 보세요."
- "평소 받는 **카톡 발주 하나만 붙여넣어 보시고**, 총 발주표가 바로 나오는지 봐주세요."
- "이게 하루에 **10~20분이라도 줄여주면 월 3만 원** 가치가 있을까요?"

> 톤: 대체/전환 압박 금지. "기존 업무 + 보조"로 접근(R4 완화).

## 8. 기능 우선순위 재확인 (영업/검증용 MVP 기준)

| 순위 | 기능 | 비고 |
|---|---|---|
| 1 | **샘플 데이터** | 시연 즉시 가능해야 함(없으면 영업 불가) |
| 2 | 거래처/품목/단가 빠른 등록 | 세팅 대행 효율 |
| 3 | **발주 붙여넣기** | 핵심 가치 |
| 4 | 파싱 결과 수정 | 반자동 신뢰 |
| 5 | **품목별 합산표** | "이거 편한데?" 포인트 |
| 6 | 거래처별 주문표 | 납품 준비 |
| 7 | 거래명세서 미리보기 | 보조 가치 |
| 8 | 미수금/세금계산서 | **후순위 검증**(2차) |

→ 기존 기능정의서 F1~F13 대비 **"샘플 데이터(1순위)"와 "빠른 세팅"의 영업적 비중이 상승**한다.

---

## 9. 판매 전환 기준

아래 중 **2개 이상**이면 다음 개발 단계로 진행한다고 정의한다.

- [ ] 실제 발주 예시를 제공한다.
- [ ] 다시 테스트해보겠다고 한다.
- [ ] 초기 세팅을 맡겨도 써보겠다고 한다.
- [ ] 기존 ERP보다 발주 정리가 편하다고 말한다.
- [ ] 월 사용료를 구체적으로 언급한다.
- [ ] 지인/동종업자에게 소개 가능하다고 한다.

---

## 10. 실패 기준

- 발주 붙여넣기가 별로 편하지 않다.
- 초기 세팅이 너무 귀찮다고 한다(우리가 대행해도 가치 못 느낌).
- 합산표/거래명세서만으로는 돈 낼 이유가 없다고 한다.
- 기존 ERP에서 충분하다고 한다.
- 실제 발주 데이터를 주기 꺼린다(신뢰/보안 장벽).

> 실패 신호가 반복되면 기능 추가보다 **타깃·문제 정의를 재검토**한다.

---

## 11. 다음 개발에 반영할 요구

- **샘플 데이터 기능은 필수**(영업 1순위).
- 초기 **세팅 대행을 고려한 관리자/입력 편의** 필요(우리가 빠르게 넣을 수 있는 화면).
- **엑셀 업로드는 후순위지만 강한 후보**(세팅 대행 효율).
- **거래처 주문 링크보다 사장님 본인 업무 단축을 먼저 검증**(Q5 후순위 유지).
- MVP 화면은 "가입 후 알아서 쓰세요"가 아니라 **"시연/세팅/검증"에 맞춘다**(온보딩 ≠ 셀프서비스).

## 12. W23 검증 보강 (2026-07-11 추가)

실사용 인터뷰(사용자 1명)에서 확인된 새 가설을 검증 질문에 추가한다. **원칙: 기존 수작업 10분을 화면으로 복제하는 것이 목표가 아니라, 같은 업무에서 중복 입력과 수정 횟수가 줄어드는지를 검증한다.**

**추가 검증 질문:**
- [ ] 단가표를 완성하지 않은 상태에서 **오늘 주문의 수량 업무(확인→합산→매입처 발주)**가 실제로 진행되는가?
- [ ] 매입처 명세서를 받은 뒤 **품목별 매입가 1회 입력 → 거래처별 판매가 훑기**가 기존 "명세서마다 금액 수동 타이핑"보다 빠른가?
- [ ] 판매가 제안(거래처 단가 > 기본 출고단가)을 사용자가 실제로 **수락**하는가, 아니면 대부분 다시 입력하는가?(대부분 재입력이면 제안 규칙 재설계 신호)
- [ ] `숙주1`류 단위 생략 발주에서 **한 번 고친 해석이 다음에 제안**되면 수정 횟수가 줄어드는가?(R6 이후)

**정량 지표(전/후 비교 — R2~R3 실측 시 기록):**
- 발주 1건 처리의 **입력 단계 수**(붙여넣기→명세서까지 클릭/입력 횟수)
- 같은 값의 **중복 입력 횟수**(예: 같은 품목 단가를 거래처 수만큼 입력했는가 → 1회로 줄었는가)
- 파싱 결과 **수정 횟수**(라인당 수정 필드 수 — 해석 기억 도입 전후)
- 명세서 N장 완성까지의 **경과 시간**(기존 약 10분 기준선)

**중단 기준:** 두 경로 도입 후 기존 경로 A 사용자의 처리 시간이 늘면(단계 추가·혼란) UI를 재설계한다. 가격 마감 화면을 실사용자가 2주 이상 쓰지 않으면 경로 B의 가치 가설을 재검토한다.
