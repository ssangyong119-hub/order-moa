## 2. 사용자 확인으로 확정된 새 방향

아래는 아이디어가 아니라 이번 문서 개편의 source of truth다.

### 2.1 제품과 플랫폼

- 오더모아는 전체 ERP가 아니라 중간 납품업자의 발주 취합→매입처 발주→가격 마감→거래명세서 반복 업무를 줄이는 좁은 반응형 웹 업무 도구다.
- 현재 Next.js 웹 하나로 모바일과 PC를 모두 지원한다.
- 네이티브 앱, PWA, 플레이스토어 배포는 지금 구현·설계 범위에서 제외하고 미래 선택지로만 기록한다.
- 기존 사이드바·메뉴·화면을 전면 교체하지 않는다.
- 사용자에게 승인받은 시각 변경은 대시보드 홈을 `오늘 업무` 중심으로 바꾸는 것이다.
- 기존 화면은 시각적 전면 개편이 아니라 빠른 수정·검색·일괄 처리·모바일 반응형 등 사용성 개선 중심으로 설계한다.

### 2.2 실제 업무에서 확인된 문제

- 카톡 발주는 `숙주1`, `콩나물2`, `단배추3`, `김치10kg`처럼 단위·규격이 생략될 수 있다.
- 같은 표현도 거래처마다 뜻이 다를 수 있고, 정답은 사용자 경험과 거래처 관습에 있다.
- 파서를 더 공격적으로 자동화하기보다 후보 제안→사람 확인→반복 해석 보조가 맞다.
- 사용자는 1,500개 품목 단가를 계속 최신으로 유지할 자신이 없으며, 실제로는 매입처 거래명세서를 받은 뒤 품목별 매입가를 보고 판매가를 그때그때 조정한다.
- 마진은 거래처 고정도 품목 고정도 아니며 상황에 따라 달라진다.
- 매입처 거래명세서는 대부분 카톡 사진으로 온다.
- 종이 발주표 사진을 보내는 거래처 사례는 현재 한 곳이며, 엑셀/파일 제공 가능성은 미확인이다.
- 한 사용자의 습관을 제품 전체 정답으로 만들지 않는다. 공통 문제는 핵심에, 개인적 방식은 선택 경로에 둔다.

### 2.3 선택형 두 경로

1. **가격 포함 바로 확정**
   - 기존처럼 품목·수량·단위·판매가를 확인하고 최종 주문을 확정한다.
2. **수량 먼저 확인, 가격 나중 확정**
   - 품목·수량·단위를 먼저 확인한다.
   - 판매가가 없어도 품목별 합산과 매입처 발주 문장을 만들 수 있다.
   - 매입처 거래명세서를 받은 뒤 실제 매입가와 참고 단가를 보고 판매가를 수정·마감한다.
   - 가격 마감 후에만 최종 주문을 확정하고 거래처 거래명세서를 만든다.

기존 빠른 경로를 없애거나 모든 사용자를 수량 확인·가격 나중 확정 경로로 강제하지 않는다.

### 2.4 가격 원칙

- `customer_prices`, `products.base_sale_price`, 최근 판매가는 제안값이다.
- 실제 또는 오늘 매입가는 가격 마감의 참고값이다.
- 고정 마진 공식으로 자동 확정하지 않는다.
- 매입가·판매가·참고 마진 금액/비율을 보여주되 최종 판매가는 사용자가 결정한다.
- `이번 주문만 변경`과 `거래처 기본 단가에도 저장`을 구분한다.
- 예상 마진은 회계 마진으로 저장하지 않는다.
- 최종 확정된 `order_items.unit_price`는 확정 시점 스냅샷이며 과거 주문·명세서를 재계산하지 않는다.

### 2.5 수정 UX 원칙

- 거래처·품목·수량·단위·매입처·매입가·판매가를 현재 업무 화면에서 쉽게 수정할 수 있어야 한다.
- 기준정보 화면을 반복 왕복하지 않게 한다.
- Enter 다음 칸, 검색 선택, 선택 행 일괄 변경, 변경된 값 강조, 저장 상태, 자동 임시저장 또는 이탈 경고를 설계한다.
- 최종 확정 전에는 편하게 수정하고 최종 확정 뒤에는 조용한 덮어쓰기가 아니라 정정 절차를 사용한다.
- 불편한 자동화보다 빠른 수동 수정이 우선이다.

### 2.6 OCR 경계

- OCR은 즉시 구현 대상이 아니다.
- 먼저 표 복사·CSV·엑셀 제공 가능성을 확인한다.
- 향후 OCR은 두 개의 별도 실험으로 나눈다.
  1. 거래처 발주표 사진→품목·규격·거래처·수량·단위 추출 및 합산
  2. 매입처 명세서 사진→품목·수량·매입단가·금액 추출 및 가격 마감 후보
- 원본 이미지에는 상호·전화·사업자번호가 포함될 수 있으므로 기본 영구저장 금지, 임시 처리·삭제·사용자 검수·낮은 신뢰도 차단을 설계한다.
- OCR, 카톡 자동 읽기, 이카운트 연동을 핵심 흐름과 결합하지 않는다. 입력 어댑터 경계로 둔다.

### 6.2 화면·UX

- `docs/screen-specification.md`

대시보드 승인 구조:

```text
오늘 업무                               미처리 N건
[새 발주] [매입처 발주] [가격 대기] [명세서 준비]

지금 먼저 할 일
- 거래처 · 품목 N개 · 단위 확인 N       [열기]

- 매입명세서 N건 · 판매가 마감 필요      [가격 마감]
```

UI 경계:

- 기존 좌측 사이드바·메뉴·화면은 유지
- 대시보드는 진행판이 아니라 실제 주문 상태 기반 업무 큐
- 대시보드는 별도 상태를 저장하지 않고 도메인 상태를 집계
- 모바일은 한 열 카드/목록, 가로 넘침 금지
- 현재 모바일의 상단 메뉴 넘침, 대시보드 제목 줄바꿈, 계정/로그아웃 충돌을 수정 대상으로 기록
- 기존 화면은 인라인 수정·검색·일괄변경·키보드 이동·저장상태 중심으로 보강
- 카드 남발·중첩 카드·마케팅형 대형 히어로 금지
- PC 가격 마감은 조밀한 표와 키보드 효율, 모바일 발주 검수는 큰 터치 영역과 핵심 필드 우선

벤치마킹은 MarketMan, inFlow, Sortly 같은 현장 운영 도구에서 다음 원칙만 가져오고 기능을 복제하지 말 것:

- 모바일은 현장 행동을 먼저 보여준다.
- PC는 상세 조회·가격·문서 작업에 밀도를 준다.
- 검색과 예외 수정이 빠르다.
- 오늘 처리할 작업과 미완료 상태가 명확하다.

필요하면 공식 공개 화면만 참고하고 출처 URL과 관찰·추론을 구분해 문서에 기록한다.

다음 두 안 이상을 비교할 것:

1. 기존 `ordermoa_orders` 상태를 확장하고 최종 확정 전 라인을 수정
2. 별도 주문 초안/가격 마감 객체를 저장하고 최종 확정 시 기존 orders/order_items 생성

비교 기준:

- 기존 확정 주문 호환성
- `unit_price` 스냅샷 안전성
- 가격 없이 합산 가능한지
- 매입처 발주 상태 추적
- 재시도·부분 실패 복구
- RLS·company_id·교차회사 검사
- 쿼리와 화면 복잡도
- additive/idempotent 마이그레이션 가능성
- 기존 데이터 backfill 필요 여부

하나를 권장안으로 선택하되 구현 승인으로 간주하지 말 것. 실제 마이그레이션은 별도 세션과 Codex 승인 게이트다.

용어/상태 후보:

- 입력 중
- 수량 확인
- 매입처 발주 준비/완료
- 가격 대기
- 최종 확정
- 취소
- 정정

각 상태의 허용 수정, 합산 포함 여부, 거래명세서 가능 여부, 다음 전이를 상태표로 작성한다.

실제 매입가를 영구 저장할지, 당일 가격 마감 작업에만 보관할지도 비교·권장안을 제시한다. 정확 회계·재고평가·원가회계로 확대하지 말 것.

## 8. 문서 자체 QA

개편 후 반드시 수행:

1. 다음 용어의 정의가 문서마다 같은지 검색:
   - 주문 확정
   - 수량 확인
   - 가격 대기
   - 가격 마감
   - 최종 확정
   - 매입처 발주
   - 거래명세서
   - 기본 출고단가
   - 예상 마진
   - OCR
2. `order_items.unit_price` 스냅샷과 충돌하는 문장이 없는지 확인.
3. 과거 명세서가 customer_prices/base_sale_price/매입가로 재계산된다는 문장이 없는지 확인.
4. OCR이 당장 구현되거나 자동 확정된다는 문장이 없는지 확인.
5. 플레이스토어/PWA가 현재 작업 범위로 들어오지 않았는지 확인.
6. 전체 ERP·정확 회계·재고평가로 범위가 확장되지 않았는지 확인.
7. 기존 확정 주문과 0001~0009 마이그레이션을 되돌리거나 파괴하는 제안이 없는지 확인.
8. 새 기능마다 현재/설계/미구현 상태가 표시되는지 확인.
9. 문서 링크와 기능/화면/모듈 ID 추적성이 유지되는지 확인.
10. `git diff --check` 통과.

가능하면 문서 정합성 검사 스크립트가 이미 있으면 사용하고, 없으면 이번 세션에 새 스크립트를 만들지 말고 검색 결과를 보고한다.

## 9. 자체 리뷰·개선 아이디어·디버깅

구현이 없더라도 작업이 끝났다고 바로 멈추지 말고 다음을 수행한다.

### 자체 리뷰

- 변경 문서를 처음부터 다시 읽는다.
- 같은 사실이 서로 다른 차수·상태로 기록된 곳을 찾는다.
- 한 사용자 피드백에 과적합한 기능을 찾아 선택형 또는 실험으로 분리한다.
- 현재 코드가 지원하지 않는 기능을 완료라고 쓰지 않는다.
- 불변 규칙, `ordermoa_` 접두사, RLS, raw_text 삭제 가능, 예상 마진 비저장, unit_price 스냅샷을 재확인한다.

### 디버깅

- JSON 유효성, 진행판 생성, 문서 링크, 번호·표·용어 오류를 추적한다.
- 문제 발견 시 문서 범위 안에서 최소 수정한다.
- 앱 코드의 기존 버그를 발견해도 이번 세션에서는 수정하지 말고 `Codex 검수 포인트`에 근거와 위치만 기록한다.

### 개선 아이디어

- 즉시 문서 반영할 것
- 후속 설계가 필요한 것
- 사용자 실측 후 결정할 것
- 범위 밖이라 제외할 것

네 범주로 나눈다. 승인 없이 앱 기능으로 구현하지 않는다.

## 10. 검증

코드를 변경하지 않았더라도 현재 기준선이 깨지지 않았음을 확인한다.

- 루트 `npm test`
- `cd web && npm test`
- `cd web && npm run build`
- `cd web && npm audit --audit-level=low`
- `git diff --check`
- `git status --short`

브라우저 smoke는 앱 코드를 바꾸지 않으므로 필수는 아니지만, 화면 설계서가 현재 메뉴와 충돌하는지 확인하려면 읽기 전용으로 현재 UI를 확인해도 된다. `.env.local` 수정·이동 금지.
