# 오더모아 제품 정의 초안

작성일: 2026-05-26

## 1. 제품명

현재 가칭: 오더모아

의미:

- 여러 거래처에서 들어오는 주문을 모은다.
- 모은 주문을 도매상 발주, 거래처별 납품, 거래명세서, 정산으로 이어준다.
- 소상공인에게 직관적인 이름이다.

이름 리스크:

- 검색 결과 `오더모아`라는 법인명이 이미 확인된다.
- 현재 공개 검색만으로 동일 서비스인지, 상표 등록 여부가 있는지는 확정할 수 없다.
- 최종 브랜드 확정 전 KIPRIS 상표 검색, 도메인, 앱 이름, 사업자명 중복 확인이 필요하다.

결론:

- 당분간 내부 프로젝트 가칭으로 `오더모아`를 사용한다.
- 외부 공개 전 최종 브랜드명은 다시 검토한다.

## 2. 한 문장 정의

오더모아는 식당과 소매 거래처에서 들어온 발주를 취합해 도매상 발주 리스트, 거래처별 거래명세서, 미수금, 세금계산서 정리까지 한 번에 관리하는 중간 납품업자 전용 ERP다.

## 3. 대상 사용자

주 대상:

- 식당, 카페, 반찬가게, 마트 등에 식자재나 공산품을 납품하는 중간 도소매업자

확장 대상:

- 농산물, 축산, 수산, 공산품 도매업자
- 경매 도매를 보고 식당에 재납품하는 사업자
- 소규모 제조 후 거래처에 반복 납품하는 사업자

## 4. 사용자의 위치

사용자는 단순 판매자가 아니라 중간 정리자다.

업무 흐름:

```text
식당/거래처 발주
→ 주문 취합
→ 도매상/시장/공급처 발주
→ 물건 확보
→ 거래처별 납품 준비
→ 거래명세서 발행
→ 납품
→ 미수금/입금 확인
→ 세금계산서/월말 정산
```

## 5. 해결할 핵심 문제

1. 거래처 발주가 카카오톡, 전화, 사진, 문자 등으로 흩어진다.
2. 발주 내용을 ERP에 다시 입력해야 한다.
3. 사진으로 온 주문은 사람이 보고 받아 적어야 한다.
4. 여러 거래처 주문을 상품별 총 물량으로 다시 합산해야 한다.
5. 거래처별 단가가 달라 실수 가능성이 있다.
6. 거래명세서, 미수금, 세금계산서, 월말 정산이 이어져 있지만 따로 관리된다.

## 6. 제품 방향

초기에는 이카운트 같은 범용 ERP 전체와 정면 경쟁하지 않는다.

대신 중간 납품업자의 실제 업무 순서대로 필요한 기능만 좁고 깊게 만든다.

최종 목표는 사용자가 이카운트의 넓은 기능 중 일부만 쓰는 상황이라면, 오더모아만으로 해당 핵심 업무를 처리할 수 있게 하는 것이다.

## 7. MVP 범위

첫 MVP는 다음 기능을 목표로 한다.

1. 거래처 등록
2. 품목 등록
3. 거래처별 판매 단가 등록
4. 거래처별 발주 입력
5. 카카오톡 발주 복사/붙여넣기 정리
6. 사진 발주 OCR 보조
7. 상품별 총 발주/출고 합산표
8. 거래처별 납품표
9. 거래명세서 생성

첫 버전에서 제외할 가능성이 높은 기능:

- 카카오톡 메시지 자동 읽기
- 세금계산서 직접 발행
- 은행 계좌 자동 입금 매칭
- 이카운트 직접 연동
- 완전 자동 OCR 처리

이유:

- 외부 서비스 권한, 법적/정책적 제약, 정확도 문제가 있다.
- 첫 버전은 사람이 확인하고 수정하는 반자동 흐름이 더 현실적이다.

## 8. 2단계 기능

1. 매입처/도매상 발주 관리
2. 매입 단가 관리
3. 판매 단가와 매입 단가 비교
4. 품목별 마진 확인
5. 단가 변경 이력
6. 품절/대체품 관리
7. 배송/출고 상태 관리

## 9. 3단계 기능

1. 거래처별 미수금
2. 입금 상태
3. 오래된 미수금 알림
4. 월별 거래처 정산서
5. 세금계산서 발행 금액 부족/초과 관리
6. 세무사 전달용 자료 정리

## 10. 중요한 설계 원칙

1. 사장님이 매일 쓰는 화면을 먼저 만든다.
2. ERP 용어보다 현장 용어를 쓴다.
3. 완전 자동보다 빠른 확인/수정이 가능한 반자동을 우선한다.
4. 거래처의 행동 변화를 처음부터 강요하지 않는다.
5. 카톡, 사진, 전화 주문처럼 현실의 지저분한 입력을 받아들인다.
6. 출고 합산표와 거래명세서를 핵심 가치로 둔다.
7. 나중에 미수금과 세금계산서로 확장할 수 있게 데이터 구조를 잡는다.

## 11. 당장 확인할 질문

설문 결과와 추가 인터뷰에서 다음을 확인한다.

- 이카운트 또는 유사 ERP를 쓰는 사람이 실제로 어떤 기능만 쓰는가?
- 카톡/사진/전화 발주를 다시 입력하는 일이 얼마나 자주 있는가?
- 상품별 총 물량 합산이 얼마나 번거로운가?
- 거래처별 단가 실수가 실제 손해로 이어지는가?
- 거래명세서 생성만으로 이카운트 대체 의사가 생기는가?
- 미수금과 세금계산서 기능이 없으면 월 사용료를 내기 어려운가?
- 거래처용 주문 링크를 실제 거래처가 써줄 가능성이 있는가?

## 12. 현재 작업 방식

기획/자료:

- Google Drive에 프로젝트 폴더를 만들고 자료를 모은다.
- 설문 결과, 캡처, 통화 메모, 경쟁사 조사, 화면 스케치를 저장한다.

개발/문서:

- 로컬 프로젝트 `D:\Documents\ERP-1`에서 추적 문서와 코드 작업을 진행한다.
- 중요한 결정은 `docs` 폴더에 Markdown으로 남긴다.

권장 Google Drive 구조:

```text
오더모아/
├─ 01_기획문서/
├─ 02_설문결과/
├─ 03_현장자료_캡처/
├─ 04_경쟁사조사/
├─ 05_화면설계/
└─ 06_회의메모/
```

## 13. MVP 0.1 구현 범위

첫 구현은 브라우저에서 바로 열 수 있는 정적 프로토타입이다.

포함 기능:

- 거래처 등록
- 품목 등록
- 거래처별 판매 단가 등록
- 거래처별 발주 입력
- 도매상 발주용 상품별 총 물량 합산
- 거래처별 거래명세서 미리보기
- JSON 자료 내보내기/가져오기

제외 기능:

- 실제 세금계산서 발행
- 계좌 입금 자동 매칭
- 카카오톡 자동 읽기
- 사진 OCR 자동 추출
- 이카운트 직접 연동

목적:

- 설문 결과가 도착하기 전까지 제품 흐름을 눈으로 확인한다.
- 친구 업무 흐름을 기준으로 첫 화면과 핵심 데이터를 검증한다.
- 추후 설문 결과에 따라 미수금, 세금계산서, OCR, 거래처 주문 링크 중 우선순위를 정한다.
