# 오더모아 운영 UX · 품목코드 · 과세구분 고정 설계

작성일: 2026-07-11
상태: **사용자 합의 완료. 이후 세션의 기능 판단 기준**
상위 기준: `docs/order-moa-system-meta-prompt.md`, `docs/order-moa-system-redesign-2026-07-11.md`
선행 조건: W23-R3 및 0011 가격 마감 가드의 Codex 검수·커밋·DB 실측을 먼저 마친다.

## 1. 왜 이 설계가 필요한가

오더모아는 "완벽한 단가표를 먼저 만드는 ERP"가 아니라, 발주를 모아 수량을 정리하고 매입처에 발주한 뒤 사람의 판단으로 판매가격을 마감하는 업무 도구다. 따라서 화면은 사용자의 예외 판단을 빠르게 돕되, 최종 확정 주문을 조용히 바꾸면 안 된다.

이번 설계는 아래 실사용 요구를 하나의 규칙으로 정리한다.

1. 확정 주문도 실수는 생기므로 정정 경로가 있어야 한다.
2. 숫자 입력, 기본단가 확인, 매입처 발주 문장 편집은 화면 안에서 빠르게 끝나야 한다.
3. 모든 품목은 사람이 식별할 수 있는 오더모아 품목코드를 가져야 한다.
4. 품목별 면세·과세는 품목 마스터에서 관리하고, 최종 명세서에는 확정 시점 값을 사용해야 한다.
5. 매입처 발주는 기본값을 제안할 뿐, 이번 발주만 다른 매입처를 고르는 일을 막지 않는다.

## 2. 고정 제품 원칙

- 웹 한 벌을 모바일과 PC에서 쓴다. 네이티브 앱·PWA·플레이스토어는 이번 범위가 아니다.
- 파서는 초벌 제안이며, 품목·단위·매입처·판매가는 사람이 현장에서 고칠 수 있어야 한다.
- `order_items.unit_price`는 **최종 판매가 확정 시점의 공급가 단가** 스냅샷이다. 현재 단가표·기본단가·매입가를 과거 주문에 다시 적용하지 않는다.
- 예상 마진은 참고 계산만 하며 저장하지 않는다. 회계 마진·세금계산서 직접 발행·재고평가를 만들지 않는다.
- `source_code`는 이카운트 등 외부 파일의 품목코드이며 import 멱등 매칭용이다. 오더모아 자체 품목코드와 섞지 않는다.
- 매입처 문장은 복사해서 카카오톡 등에 보내는 보조 도구다. 자동 전송·카카오톡 연동은 만들지 않는다.

## 3. 우선순위와 작업 분해

### R5a — 즉시 체감 UX 팩 (첫 구현, 마이그레이션 없음)

1. 단가 입력 전체선택·Enter 이동
2. 단가 관리의 기본 출고단가·실제 적용 단가 표시
3. 매입처 발주 문장 날짜·수정·초기화
4. 합산표에서 이번 발주만 매입처를 바꾸는 선택

R5a는 이미 저장된 주문 스냅샷, 상태 모델, 테이블 구조를 바꾸지 않는다. W23-R4 대시보드보다 앞서 진행할 수 있는 작은 안전 팩이다.

### R5b — 확정 주문 정정 (별도 승인·별도 마이그레이션)

최종 확정 주문의 라인을 직접 수정하지 않는다. 주문 목록에서 `정정`을 누르면 다음 흐름을 제공한다.

```text
기존 최종 확정 주문 선택
→ 취소 확인 (기존 주문은 cancelled로 보존)
→ 원래 품목·수량·단가를 새 편집 화면에 복사
→ 수정 후 새 주문으로 최종 확정
→ 새 주문은 기존 주문을 정정한 주문임을 연결
```

새 주문에는 `corrected_from_order_id` 같은 원주문 연결을 저장한다. 취소 주문은 합산표·월합계·일반 업무 목록에서 제외하되, 주문 이력에서는 "정정됨"으로 추적 가능해야 한다. 기존 거래명세서는 바뀌지 않고, 새 주문의 명세서를 다시 발행한다.

### W24 — 품목코드·과세구분 기반 (별도 승인·별도 마이그레이션)

이 단계는 기존 0011 이후의 다음 마이그레이션 번호를 사용한다. 0011의 커밋·적용 상태를 먼저 확인하고, 번호를 확정한다.

1. 오더모아 자체 품목코드
2. 품목 과세구분과 최종 주문 라인의 과세구분 스냅샷
3. 혼합 면세·과세 거래명세서 합계 구조
4. 이카운트 품목마스터의 과세구분 컬럼이 있을 때의 import 보강

## 4. R5a 화면·동작 계약

### 4.1 가격 입력

- 파싱 확인, 가격 마감, 단가 관리의 금액 입력칸은 포커스를 받으면 현재 숫자 전체를 선택한다.
- Enter를 누르면 다음 금액 입력칸으로 이동하고, 이동한 값도 전체 선택한다.
- 사용자가 숫자를 바로 입력하면 기존 `0` 또는 기존 금액을 덮어쓴다.
- blur 시 정수 KRW로 정규화해 `05` 같은 선행 0 표기를 없앤다. 빈 값·음수·NaN·무한대는 기존 저장 차단 규칙을 유지한다.

### 4.2 단가 관리의 세 값

단가 관리 화면은 거래처별 예외 단가를 편집하는 곳이다. 다음 세 값을 나란히 보여 혼동을 없앤다.

| 값 | 의미 | 편집 |
|---|---|---|
| 거래처별 단가 | `customer_prices.sale_price` | 이 화면에서 편집 |
| 기본 출고단가 | `products.base_sale_price` | 표시만. 변경은 품목·별칭 관리에서 수행 |
| 현재 적용 단가 | 거래처별 단가가 있으면 그것, 없으면 기본 출고단가 | 읽기 전용 |

`미등록`은 두 값이 모두 없을 때만 쓴다. 기본 출고단가가 있으면 `기본 단가 적용 중`으로 보인다. 이렇게 해도 가격 우선순위는 변하지 않는다.

```text
거래처별 단가 > 기본 출고단가 > 미등록(0원)
```

### 4.3 매입처 발주 문장

문장 생성 기본값은 아래 형식이다.

```text
2026-07-11
오더모아유통입니다 발주 품목입니다

1. 위생장갑 7박스
2. 키친타월 6박스
```

- 날짜는 합산표가 적용 중인 발주일을 사용한다. 전체 보기처럼 날짜가 하나가 아니면 오늘 날짜를 제안하고 사용자가 문장에서 고친다.
- 매입처별 문장은 편집 가능한 textarea로 제공한다. 수정본은 **현재 화면·복사 작업에만** 남기며 DB 템플릿으로 저장하지 않는다.
- 체크 품목·매입처 변경 뒤에는 문장을 자동으로 덮어쓰지 않는다. `문장 다시 만들기`를 명시적으로 눌러 새 목록으로 재생성하고, 수정한 문장이 있으면 확인을 받는다.
- `이 매입처만 복사`와 전체 문장 복사를 유지한다.

### 4.4 이번 발주만 매입처 변경

- 합산표 행의 매입처 이름 또는 `미지정` 배지를 누르면 활성 매입처 선택 목록을 연다.
- 선택은 `aggregate row key(productId + unit)` 단위의 **이번 발주용 임시 재배정**이다. 기본 매입처를 즉시 바꾸지 않는다.
- 재배정 뒤 매입처별 수량, 누락 카운터, 발주 문장은 즉시 다시 묶인다.
- 사용자가 원할 때만 `앞으로 기본 매입처로도 저장` 명령을 별도 확인 후 실행한다. 이 명령만 `products.purchase_supplier_id`를 바꾼다.
- 보관된 매입처는 선택 목록에 넣지 않는다.

## 5. 품목코드 정책

### 5.1 두 종류의 코드를 분리한다

| 필드 | 예시 | 목적 |
|---|---|---|
| `app_code` | `OM-000001` | 오더모아 안에서 모든 품목에 항상 있는 식별 코드 |
| `source_code` | 이카운트 품목코드 | 외부 파일 import 재실행 시 같은 품목을 찾는 코드. null 가능 |

새로 만드는 품목도 `app_code`를 반드시 받는다. 외부 코드를 모르거나 없는 것은 정상이며 `source_code`만 null이다.

### 5.2 생성·표시 규칙

- 형식은 회사별 순번 `OM-000001`, `OM-000002`로 고정한다.
- 회사 안에서 유일해야 하며, 기존 품목도 안정된 순서로 일괄 backfill한다.
- 동시 등록에서 `max(app_code) + 1`을 앱에서 계산하면 안 된다. DB의 `ordermoa_` 접두사 카운터/함수/트리거 중 하나로 원자적으로 발급한다.
- 품목·별칭 관리와 카탈로그 검수 화면에서 `app_code`와 `source_code`를 구분해 표시·검색한다.
- 앱이 발급한 `app_code`는 일반 편집으로 바꾸지 않는다. 외부 코드만 import 흐름에서 갱신한다.

## 6. 과세구분과 거래명세서

### 6.1 값과 가격의 의미

- 품목 마스터의 `tax_type`은 `미설정 | 면세 | 과세` 세 값이다. 현재 자료에 없는 값은 임의로 농산물/공산품 기준 추정하지 않고 `미설정`으로 둔다.
- W24 이후 가격 입력·기본 출고단가·거래처별 단가는 모두 **부가세 제외 공급가 단가**로 해석한다.
- 과세 품목의 VAT는 과세 라인 금액을 모두 합산한 공급가에 10%를 한 번 계산해 원 단위로 반올림한다. 면세 라인은 VAT 0원이다.

```text
면세 공급가 = 면세 라인 amount 합계
과세 공급가 = 과세 라인 amount 합계
부가세 = round(과세 공급가 × 0.10)
합계 = 면세 공급가 + 과세 공급가 + 부가세
```

이는 사용자가 합의한 업무 표시 규칙이다. 앱은 세금계산서를 발행·신고하지 않으며, 실제 세무 처리·면세 판정은 세무 전문가와 확인한다.

### 6.2 스냅샷과 출력

- `order_items`에 최종 확정 시점의 `tax_type_snapshot`을 저장한다. 품목 마스터를 나중에 바꿔도 과거 명세서 세액·합계는 바뀌지 않는다.
- 기존 주문은 과거 출력과 합계를 바꾸지 않는다. backfill 값은 `미설정`으로 두고 기존 "VAT 미적용" 양식을 유지한다.
- 새 세무 기반 주문의 거래명세서 하단은 `면세 공급가 / 과세 공급가 / 부가세 / 합계`를 구분해 표시한다. 품목 행에는 면세·과세 표시를 둔다.
- `미설정` 품목이 포함된 새 주문은 과세 합계를 추정하지 않는다. 세무 기반 거래명세서 인쇄 전에 사용자가 과세구분을 고치도록 명확히 안내한다.

### 6.3 이카운트 import 경계

- 친구의 품목마스터 export에 `과세구분` 또는 동등한 컬럼이 있을 때만 화이트리스트로 읽어 `tax_type` 후보로 쓴다.
- 고객명·매입처명·전화·주소·사업자번호는 이번 import 범위에 넣지 않는다.
- 기존 `base_sale_price`의 VAT 포함/제외 여부는 자동 변환하지 않는다. 이카운트 export의 가격 기준을 사용자가 한 번 확인한 뒤에만 별도 보정한다.

국세청 안내도 일반 매출세액을 공급가액의 10%로 설명한다. [국세청 세무 안내](https://g.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7804&mi=2483)

## 7. 검증·안전 기준

### R5a

- 기존 W23-R3 상태 전이·가격 마감·스냅샷 코드를 변경하지 않는다.
- 순수 함수 테스트: 발주 문장 날짜 렌더링, 임시 매입처 재배정 후 그룹핑, 편집본 재생성 경고.
- UI 테스트/브라우저 smoke: 숫자 입력→Enter→다음 값 전체선택, 기본 단가만 있는 품목의 상태, 미지정 매입처 재배정, 문장 수정→복사→명시 재생성.
- 390px 모바일과 데스크톱 모두에서 발주 붙여넣기·합산표를 확인한다.

### R5b/W24

- 마이그레이션은 별도 파일·별도 Codex 승인·사용자 SQL Editor 적용으로 분리한다.
- 새 DB 객체에는 `ordermoa_` 접두사, RLS 4정책, 교차회사 검증, idempotent 적용을 빠뜨리지 않는다.
- 과거 주문의 `unit_price`, `amount`, 향후 `tax_type_snapshot`은 어떤 기준정보 변경에도 재조회하지 않는다.

## 8. 비범위

- 세금계산서 발행·부가세 신고·회계 마진 저장
- 매입처 거래명세서 OCR 및 자동 매입가 반영
- 카카오톡 자동 읽기·자동 전송
- 이카운트 실시간 연동
- 다단위 환산과 품목 단위별 가격 모델

이 항목들은 현재 업무 흐름이 안정되고 실사용 근거가 생긴 뒤 각각 별도 설계·승인한다.
