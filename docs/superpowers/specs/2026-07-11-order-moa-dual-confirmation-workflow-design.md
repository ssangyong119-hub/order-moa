# 오더모아 선택형 주문 확정·가격 마감 재설계

작성일: 2026-07-11
상태: 사용자 방향 승인, 상세 기획 문서 개편의 기준
적용 범위: 제품 정의·요구사항·기능·화면·데이터·로드맵 설계
비적용 범위: 이번 문서만으로 코드·DB 마이그레이션·OCR·PWA·플레이스토어를 구현하지 않는다.

## 1. 결정 배경

실사용 인터뷰에서 기존 설계의 두 가정이 현실과 다를 수 있음이 확인됐다.

1. `숙주1`, `콩나물2`처럼 단위와 규격이 생략된 발주는 문장만으로 정답을 복원할 수 없다. 거래처별 관습과 사용자의 판단이 필요하다.
2. 판매단가는 1,500개 품목의 고정 단가표를 항상 관리해서 결정되는 것이 아니라, 많은 경우 매입처 거래명세서를 받은 뒤 실제 매입가와 품목 상황을 보고 사용자가 그때그때 정한다.

한 사용자의 현재 습관을 그대로 복제하지는 않는다. 대신 여러 사용자에게 공통일 가능성이 높은 문제를 제품 중심에 반영한다.

- 입력은 불완전하고 문맥 의존적이다.
- 수량을 먼저 알아야 매입처에 발주할 수 있다.
- 판매가격은 수량 확인보다 늦게 결정될 수 있다.
- 최종 거래명세서는 사람이 확인한 판매가격으로 만들어야 한다.
- 사용자는 예외만 빠르게 수정할 수 있어야 한다.

## 2. 새 제품 정의

오더모아는 카톡·문자·표·사진 등으로 흩어진 거래처 발주를 사람이 빠르게 확인할 수 있는 주문 초안으로 정리하고, 품목별 합산과 매입처 발주를 거쳐, 판매가격이 준비된 주문은 즉시 확정하고 준비되지 않은 주문은 매입가 확인 후 가격을 마감해 거래명세서까지 연결하는 중간 납품업자용 반응형 웹 업무 도구다.

제품 중심은 `파싱 정확도` 하나가 아니라 다음 네 단계다.

```text
모으기 → 해석·수량확인 → 합산·매입처 발주 → 가격 마감·거래명세서
```

오더모아는 전체 ERP가 아니다. 회계·세무·재고평가를 대체하지 않고, 중간 납품업자의 발주 취합부터 거래명세서 작성까지 반복 입력을 줄인다.

## 3. 확정된 제품 원칙

1. 웹 하나로 모바일과 PC를 모두 지원한다. 네이티브 앱·PWA·플레이스토어는 현재 범위가 아니다.
2. 기존 사이드바·화면·기능을 전면 교체하지 않는다. 대시보드는 `오늘 할 일` 중심으로 재설계하고, 기존 화면은 사용성 개선 위주로 보강한다.
3. 사용자는 두 경로 중 하나를 선택할 수 있다.
   - 가격 포함 바로 확정
   - 수량 먼저 확인 후 가격 나중 확정
4. 파서는 정답을 자동 결정하지 않는다. 후보를 제안하고 사용자가 확인한다.
5. 단위·품목·매입처·가격 변경은 가능한 한 현재 업무 화면 안에서 즉시 처리한다.
6. `이번 주문만 변경`과 `앞으로 기본값으로 저장`을 명확히 구분한다.
7. 최종 확정된 `order_items.unit_price`는 계속 불변 스냅샷이다.
8. 마진율은 거래처·품목·시점에 따라 달라질 수 있으므로 강제 공식이나 고정 마진을 전제하지 않는다.
9. 매입가·기본 출고가·최근 판매가·거래처별 단가는 판매가 결정을 돕는 제안값이다. 최종 결정은 사용자에게 있다.
10. 예상 마진은 참고 계산이며 회계 마진으로 저장하지 않는다.
11. OCR은 핵심 아키텍처가 아니라 입력 어댑터 후보다. 구조화 파일·표 복사를 우선 검토하고, 사진 OCR은 별도 실험을 통과한 뒤 착수한다.
12. 카톡 자동 읽기, 이카운트 자동 연동, 세금계산서 직접 발행, 전체 재고 ERP는 계속 제외 또는 후순위다.

## 4. 선택형 핵심 흐름

### 4.1 공통 시작

```text
거래처 선택
→ 카톡/문자 원문 붙여넣기
→ 품목·수량·단위 후보 생성
→ 미매칭·다중후보·단위불확실 라인을 사람이 수정
```

### 4.2 빠른 확정 경로

판매가격이 이미 준비된 경우:

```text
수량·단위·판매가 확인
→ 최종 주문 확정
→ 품목별 합산·매입처 발주
→ 거래명세서 조회·인쇄
```

현재 구현된 흐름의 연속성을 유지한다.

### 4.3 수량 먼저 확인·가격 나중 확정 경로

판매가격이 준비되지 않은 경우:

```text
수량·단위만 먼저 확인
→ 가격 대기 주문으로 저장
→ 가격과 무관하게 품목별 합산
→ 매입처별 발주 문장 전송
→ 매입처 거래명세서 수신
→ 실제 매입가 입력 또는 추출 결과 검수
→ 품목별·거래처별 판매가 제안 확인·수정
→ 가격 마감
→ 최종 주문 확정
→ 거래처 거래명세서 조회·인쇄
```

가격 대기 상태는 최종 주문 확정과 다르다. 최종 확정 전에는 수정 가능하지만, 최종 확정 뒤에는 단가를 조용히 재계산하거나 덮어쓰지 않는다.

## 5. 상태와 데이터의 행동 계약

정확한 DB 구현 방식은 코드·마이그레이션 감사 후 별도 설계에서 확정한다. 다만 사용자에게 보이는 상태와 불변 규칙은 다음과 같이 고정한다.

| 상태 | 의미 | 합산·매입처 발주 | 거래명세서 | 수정 |
|---|---|---|---|---|
| 입력 중 | 원문과 파싱 후보를 검수 중 | 제외 | 불가 | 자유 |
| 수량 확인 | 품목·수량·단위가 확인됨 | 포함 가능 | 불가 | 수량·단위·매입처 가능 |
| 매입처 발주 준비/완료 | 매입처에 보낼 수량이 정리됨 | 포함 | 불가 | 최종 확정 전 가능 |
| 가격 대기 | 판매단가가 아직 최종 결정되지 않음 | 포함 | 불가 또는 워터마크 미리보기만 | 매입가·판매가 가능 |
| 최종 확정 | 판매단가가 스냅샷으로 고정됨 | 포함 | 가능 | 정정 절차만 |
| 취소 | 업무에서 제외된 주문 | 제외 | 취소 표시 | 복원 정책 별도 |

설계 검토 시 다음 두 저장 전략을 비교하고 하나를 선택해야 한다.

- 기존 `orders`에 상태를 확장하고 최종 확정 전 라인만 수정하는 방법
- 별도 주문 초안/가격 마감 작업 객체를 두고 최종 확정 시 기존 `orders + order_items`를 생성하는 방법

선택 기준은 기존 주문 호환성, 스냅샷 안전성, 합산 성능, 구현 복잡도, RLS, 실패 복구다. 기존 확정 주문과 거래명세서는 어떤 방식에서도 변하지 않아야 한다.

## 6. 가격 마감 설계 원칙

가격 마감 화면은 단가 마스터를 유지시키는 화면이 아니라 `오늘 손볼 예외`를 처리하는 화면이다.

각 라인에 가능한 범위에서 다음 값을 나란히 보여준다.

- 실제 또는 오늘 매입가
- 품목 기본 매입가
- 품목 기본 출고가
- 해당 거래처 현재 단가
- 해당 거래처 최근 최종 판매가
- 사용자가 입력할 최종 판매가
- 참고 마진 금액과 비율

동작 원칙:

- 마진율을 고정값으로 강제하지 않는다.
- 추천 판매가를 자동 저장하지 않는다.
- 사용자가 바꾼 값과 미확정 값이 명확히 구분돼야 한다.
- Enter 이동, 여러 행 붙여넣기, 선택 행 일괄 적용 등 반복 입력을 줄인다.
- 품목 하나의 매입가가 여러 거래처 주문에 공통이면 한 번 입력해 관련 라인에 제안한다.
- 거래처별 차이는 최종 판매가에서 개별 조정할 수 있다.
- `이번 주문만`과 `거래처 기본 단가에도 저장`은 별도 명령이다.

## 7. 거래처별 해석 기억

`숙주1`을 전국 공통 규칙으로 해석하지 않는다. 장기적으로 다음 문맥을 활용해 제안한다.

- 회사
- 거래처
- 원문 별칭 또는 정규화된 표현
- 품목
- 규격·단위
- 최근 사용 기록

처음에는 사용자가 수정한다. 같은 거래처에서 반복되는 해석은 `다음부터 이 거래처 기본으로 사용`을 명시적으로 선택했을 때만 기억한다. 상황에 따라 달라지는 표현은 자동 확정하지 않고 최근 선택을 후보로 제시한다.

이 기능은 다단위 구조와 맞물리므로 수량 확인·가격 나중 확정 핵심 흐름보다 뒤 단계로 분리한다.

## 8. 입력 채널과 OCR 경계

모든 입력 채널은 공통 주문 검수표 또는 가격 마감표로 연결돼야 한다.

```text
카톡/문자 붙여넣기 ─┐
표 복사·파일 업로드 ─┼→ 공통 검수표 → 합산/가격마감
사진 OCR 후보       ─┘
```

OCR은 두 종류로 분리한다.

1. 거래처 발주표 OCR: 품목·규격·거래처·수량·단위를 추출해 합산한다.
2. 매입처 명세서 OCR: 품목·수량·단가·금액을 추출해 가격 마감 후보로 넣는다.

사진 속 상호·전화번호·사업자번호는 민감정보로 취급한다. 원본 이미지는 기본 영구 저장하지 않고, 업로드·임시 처리·삭제 정책과 사용자 검수를 먼저 설계한다. OCR 결과가 낮은 신뢰도이면 자동 반영하지 않는다.

현재 증거는 거래처 발주표 사진 요구가 한 거래처 사례라는 수준이다. OCR 구현 전에 엑셀·CSV·표 복사 가능성과 실제 사진 10~20장의 추출 정확도·시간 절감 효과를 검증한다.

## 9. UI/UX 방향

### 9.1 유지할 것

- 기존 데스크톱 좌측 사이드바
- 기존 업무 화면과 메뉴 이름
- 웹 하나로 모바일·PC를 지원하는 반응형 구조
- 조용하고 실무적인 색상과 정보 밀도

### 9.2 바꿀 것

대시보드는 제품 진행률이 아니라 오늘 처리해야 할 일을 보여준다.

```text
7월 11일 오늘 업무                         미처리 8건

[새 발주 4] [매입처 발주 2] [가격 대기 7] [명세서 준비 3]

지금 먼저 할 일
- 가람식당 · 품목 6개 · 단위 확인 1        [열기]
- 매입처 2곳 · 발주 준비                    [합산표]
- 오늘 매입명세서 2건 · 판매가 마감 필요   [가격 마감]
```

모바일에서는 같은 정보를 한 열로 배치한다. 기존 상단 메뉴 구조를 유지하되 가로 넘침, 제목 줄바꿈, 계정 정보 충돌을 해결한다. 플레이스토어형 하단 내비게이션으로 전면 교체하지 않는다.

### 9.3 모든 업무 화면의 사용성 규칙

- 현재 작업 화면 안에서 거래처·품목·단위·수량·매입처·단가를 빠르게 수정할 수 있어야 한다.
- 검색 후 선택, 키보드 Enter 이동, 일괄 변경, 실행 취소 또는 명확한 확인을 지원한다.
- 수정 때문에 기준정보 화면을 여러 번 왕복하지 않게 한다.
- 임시 작업은 자동 저장하거나 이탈 경고를 제공한다.
- 저장 중·완료·실패 상태를 분명히 보여준다.
- 모바일에서는 핵심 명령을 엄지 영역에 두고, 넓은 표는 행 카드 또는 핵심 열 고정 방식으로 변환한다.
- PC에서는 가격 마감과 명세서 작업을 위해 표 밀도와 키보드 효율을 우선한다.
- 최종 확정·삭제·취소처럼 되돌리기 어려운 행동은 다른 명령과 시각적으로 구분한다.

## 10. 모듈 변화

기존 모듈을 폐기하지 않고 다음 개념을 추가한다.

- 주문 초안/수량 확인
- 주문 상태 전이
- 가격 대기 목록
- 매입가 입력 또는 명세서 수신 작업
- 가격 마감
- 최종 확정과 정정
- 거래처별 해석 기억(후속)
- 표/파일 입력과 OCR 어댑터(검증 후)

대시보드는 이 상태들을 집계하는 읽기 전용 업무 큐다. 대시보드 자체가 별도 진실을 저장하지 않는다.

## 11. 단계별 추진 순서

1. 문서·도메인 재정의: 용어, 상태, 두 경로, 문서 권위 체계를 정리한다.
2. 상태·저장 설계: 기존 주문을 보호하는 초안/가격 대기 모델을 선택한다.
3. 수량 먼저 확인: 가격이 없어도 합산과 매입처 발주가 가능하게 한다.
4. 가격 마감: 수동 매입가 입력부터 시작하고 판매가 제안·수정·최종 확정을 연결한다.
5. 대시보드 개편: 오늘 업무 카드와 우선 처리 목록을 실제 상태에 연결한다.
6. 수정 UX 보강: 인라인 수정, 일괄 변경, 키보드 이동, 자동 저장을 핵심 화면에 적용한다.
7. 거래처별 해석 기억: 반복되는 단위·품목 해석을 명시적 저장 방식으로 보조한다.
8. 구조화 입력 확장: 표 복사·CSV를 먼저 검증한다.
9. OCR 실험: 발주표 OCR과 매입명세서 OCR을 별도 실험으로 판단한다.

각 단계는 별도 구현 계획·테스트·브라우저 실측·Codex 승인 게이트를 갖는다. 한 번의 대형 코드 변경으로 처리하지 않는다.

## 12. 성공 기준

- 가격이 없어도 수량 확인 주문이 품목별 합산과 매입처 발주에 사용된다.
- 가격이 준비된 사용자는 기존 빠른 확정 경로를 계속 사용할 수 있다.
- 가격 대기 주문은 최종 명세서 발행 전에 반드시 가격 마감을 거친다.
- 최종 확정된 과거 주문은 단가표·매입가 변경 후에도 변하지 않는다.
- 사용자가 1,500개 품목 단가를 먼저 완성하지 않아도 오늘 주문을 처리할 수 있다.
- 거래처·품목·단위·매입처·판매가 수정이 현재 업무 흐름 안에서 가능하다.
- 390px 모바일에서 발주 입력·검수·수량 확정이 가로 넘침 없이 가능하다.
- PC에서 가격 마감 시 반복적인 마우스 저장 없이 키보드 중심 입력이 가능하다.
- 실제 사용자 테스트에서 기존 수작업보다 입력 단계와 중복 입력이 줄어든다.
- OCR을 구현할 경우 낮은 신뢰도 결과가 사용자 확인 없이 주문·가격에 반영되지 않는다.
