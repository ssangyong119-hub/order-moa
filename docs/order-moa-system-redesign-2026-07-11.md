## 1. 사용자 피드백과 증거 강도

| # | 발견 | 증거 | 강도 |
|---|---|---|---|
| 1 | 카톡 발주는 단위·규격이 생략되고(`숙주1`), 해석은 거래처별 관습+사용자 판단에 있다 | 실사용자(친구) 인터뷰 2026-07-10, 실제 카톡 예시 | 중강(사용자 1명 + 설문 P1~P2와 정합) |
| 2 | 판매단가는 단가표에서 나오지 않고, 매입처 명세서 수신 후 품목별로 그때그때 정하는 경우가 많다(마진 0~20% 감) | 인터뷰 + 실제 매입처 명세서(웹/사진) 확인 | 중강(업종 구조상 일반화 가능성 높음 — 농산물 시세 변동) |
| 3 | 매입처 명세서는 대부분 카톡 **사진**으로 온다 | 인터뷰 | 중(1명 표본) |
| 4 | 종이 발주표를 사진으로 보내는 거래처가 있고, 품목별 합산을 손으로 한다 | 실물 사진(84행 발주서, 빨간펜 합산) | 약(거래처 1곳 사례) |
| 5 | 현재 수작업 전체는 약 10분 — 큰 고통은 아니나 반복 입력이 많다 | 인터뷰 | 중 |

> 표본 한계: 실사용 근거는 여전히 **사용자 1명 + 설문 5건**이다. 본 재설계는 "이 사용자 전용 복제"가 아니라 일반화 가능한 문제만 중심에 넣는다(§2).

## 2. 일반화할 문제 vs 한 사용자 습관

**여러 사용자에게 공통일 가능성이 높은 사실 → 제품 중심에 반영:**

- 입력은 불완전하고 문맥 의존적이다(단위·규격 생략).
- 수량을 먼저 알아야 매입처 발주가 가능하다.
- 판매가격은 수량 확인보다 늦게 결정될 수 있다(매입가 확인 후).
- 여러 거래처 주문의 품목별 합산은 반복 작업이다.
- 최종 거래명세서는 사람이 확인한 가격으로 만들어야 한다.

**한 사용자의 습관일 가능성이 큰 부분 → 선택 경로/실험으로 격리:**

- "거의 항상 매입 명세서를 먼저 받는" 순서 → 두 경로 중 **선택지**로 제공(강제 금지).
- 품목별 0~20% 감 마진 → 마진 자동화·저장 안 함, 참고 표시만.
- 매입 명세서가 카톡 사진으로 오는 방식 → 1차는 수동 입력, 사진 추출은 보류 실험.
- 종이 발주표 사진 거래처 1곳 → 엑셀/파일 수령 가능성 먼저 확인, OCR은 그 후 판단.

### 용어표 (전 문서 단일 소스)

| 용어 | 정의 |
|---|---|
| **수량 확인** | 품목·수량·단위까지 사람이 확인한 상태. 합산·매입처 발주 가능, 명세서 불가 |
| **가격 대기** | 수량 확인됐으나 판매단가가 최종 결정되지 않은 주문 |
| **가격 마감** | 실제/오늘 매입가와 제안값을 보고 사용자가 판매단가를 확정하는 행위 |
| **최종 확정** | 판매단가가 `order_items.unit_price` 스냅샷으로 고정되는 순간. 이후 정정 절차만 |
| **정정** | 최종 확정 뒤의 수정. 조용한 덮어쓰기 금지 — 별도 절차(설계 후속) |
| **매입처 발주** | 합산표 기반으로 매입처에 보낼 구매 문장 생성·복사(가격 불필요) |
| **거래명세서** | 우리→거래처 판매 서류. 최종 확정 주문만 발행 |
| **제안값** | customer_prices·base_sale_price·최근 판매가 등 판매가 결정을 돕는 값. 자동 확정 금지 |

## 3. 새 제품 정의와 비목표

**한 문장 정의 [설계 승인]:**

> 오더모아는 카톡·문자·표·사진으로 흩어진 거래처 발주를 사람이 빠르게 확인할 수 있는 주문 초안으로 **모으고**, 품목·수량을 **해석·확인**해 품목별 **합산과 매입처 발주**로 잇고, 판매가격이 준비된 주문은 즉시, 준비되지 않은 주문은 매입가 확인 후 **가격을 마감**해 **거래명세서**까지 연결하는 중간 납품업자용 반응형 웹 업무 도구다.

**제품 중심 4단계:** `모으기 → 해석·수량확인 → 합산·매입처 발주 → 가격 마감·거래명세서`

**비목표(불변):** 전체 ERP 아님. 세무 기장·부가세 신고·정확 회계 마진·재고평가·카톡 자동 읽기·이카운트 연동·세금계산서 직접 발행·은행 자동 매칭은 하지 않거나 후순위. 네이티브 앱·PWA·플레이스토어 배포는 현재 범위 밖(미래 선택지로만 기록).

## 4. 두 경로 업무 흐름

**공통 시작 [현재 구현]:** 거래처 선택 → 원문 붙여넣기 → 품목·수량·단위 후보 생성 → 미매칭/다중후보/수량불확실 라인 사람 수정.

**경로 A — 가격 포함 바로 확정 [현재 구현 = 유지]:**
```
수량·단위·판매가 확인 → 최종 확정 → 합산·매입처 발주 → 명세서
```
단가가 채워지는 주문(거래처 단가 또는 기본 출고단가 제안 수락)은 지금 흐름 그대로 끝난다. **기존 사용자 경험 불변.**

**경로 B — 수량 먼저, 가격 나중 [설계 승인·미구현]:**
```
수량·단위만 확인 → 가격 대기 저장 → (가격 무관) 합산·매입처 발주 문장
→ 매입처 명세서 수신 → 품목별 매입가 입력 → 판매가 제안 확인·수정
→ 가격 마감 = 최종 확정 → 명세서
```

원칙: 두 경로는 **선택**이다. 어느 쪽도 강제하지 않고, 한 주문 안에서 B→A 승격(단가가 다 차면 즉시 마감)이 자연스러워야 한다.

## 5. 상태 전이표 [설계 승인·미구현]

| 상태 | 의미 | 합산·매입처 발주 | 거래명세서 | 허용 수정 | 다음 전이 |
|---|---|---|---|---|---|
| 입력 중 | 원문·파싱 후보 검수 중(화면 상태, DB 미저장) | 제외 | 불가 | 자유 | 수량 확인 / 폐기 |
| 수량 확인(가격 대기) | 품목·수량·단위 확인, 판매단가 미확정 | **포함** | 불가(워터마크 미리보기는 후속 검토) | 수량·단위·매입처·매입가·판매가 | 최종 확정 / 취소 |
| 최종 확정 | 판매단가 스냅샷 고정 | 포함 | **가능** | 정정 절차만 | 정정 / 취소 |
| 취소 | 업무 제외(soft) | 제외 | 취소 표시 | — | (복원 정책 별도) |

- "매입처 발주 준비/완료"는 별도 DB 상태가 아니라 **합산표 화면의 파생 정보**로 시작한다(발주 이력 저장은 2차 F8 유지). 기준서 §5의 행 중 이 행만 화면 파생값으로 구현해 상태 수를 최소화한다.
- 기존 주문(현재 confirmed)은 전부 "최종 확정"으로 해석 — 마이그레이션 시 backfill 불필요한 방향을 우선한다(§11).

## 6. 가격 마감 UX와 가격 데이터 우선순위 [설계 승인·미구현]

**화면 목적:** 단가 마스터 유지가 아니라 "오늘 손볼 예외 처리". 한 품목의 매입가는 **한 번만** 입력하고, 그 품목을 시킨 여러 거래처 주문 라인에 판매가 제안이 퍼진다.

라인별 나란히 표시(가능한 범위): 오늘 매입가(입력) · 품목 기준 매입가 · 품목 기본 출고가 · 이 거래처 현재 단가 · 이 거래처 최근 최종 판매가 · **최종 판매가(입력)** · 참고 마진 금액/%.

**판매가 제안 우선순위(표시 순서이지 자동 확정 아님):**
1. 해당 거래처 현재 단가(customer_prices)
2. 품목 기본 출고단가(base_sale_price)
3. (제안 없음 — 사용자가 입력)

동작 원칙:
- 마진율 고정 공식·자동 확정·추천값 자동 저장 금지. 최종 판매가는 항상 사용자가 결정.
- `이번 주문만 변경`과 `거래처 기본 단가에도 저장`은 별도 명령(현행 파싱 화면의 "이 단가 저장" 원칙 유지).
- 마감 때 입력한 **오늘 매입가는 기본적으로 이번 가격 마감에만 사용**한다. 사용자가 `품목 기본 매입가에도 저장`을 별도로 선택한 경우에만 `products.base_purchase_price`를 갱신한다. 판매가 역시 기본값 저장은 별도 명령이다. 이렇게 명시 저장한 값만 다음 주문의 제안값으로 재사용한다.
- Enter 이동·선택 행 일괄 적용·변경값 강조·저장 상태 표시(§9 수정 UX 규칙 적용).
- 예상 마진은 표시 전용(저장 금지) — 헌장 불변 규칙 유지.

**실제 매입가 저장 범위 비교 [권장안 포함]:**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| a. 저장 안 함(화면만) | 마감 작업 중에만 사용 | 스키마 0 | 새로고침 유실, 마감 중단 복구 불가 |
| b. **명시 선택 시 products.base_purchase_price 갱신(권장)** | `품목 기본 매입가에도 저장`을 선택한 경우에만 최신 참고값으로 덮어씀(이력 없음) | 스키마 0(기존 컬럼), 반복 입력 감소, `이번 주문만/기본값 저장` 분리 유지 | 시점별 이력 없음(의도된 한계 — 2차 purchase_prices) |
| c. 매입가 이력 테이블 | 일자별 매입가 보존 | 정밀 | 2차 원가 모델 선점 — 범위 초과 |

→ **권장: b.** 단 자동 갱신은 금지하고 사용자 명시 선택을 필수로 한다. 이력이 필요해지는 순간이 2차 `purchase_prices`의 착수 신호다.

## 7. 거래처별 해석 기억 [미구현·후속 — 핵심 흐름 뒤]

- `숙주1`은 전국 공통 규칙으로 해석하지 않는다. 문맥 = 회사 × 거래처 × 표현(별칭/정규화) × 품목 × 단위 × 최근 기록.
- 처음엔 사용자가 수정. 같은 거래처에서 반복되는 해석은 **"다음부터 이 거래처 기본으로 사용"을 명시 선택했을 때만** 기억(자동 학습·자동 확정 금지).
- 기억된 해석도 후보 제안일 뿐 확정 차단 규칙(미매칭·수량불확실·다중후보)은 유지.
- 다단위(Phase 3 product_units)와 맞물리므로 **경로 B(수량·가격 마감) 구현 뒤** 별도 설계·승인으로 진행. 스키마 후보(예: 거래처×품목 기본 단위 테이블)는 그 설계 세션에서 비교한다.

## 8. 입력 채널·표/파일·OCR 경계

```
카톡/문자 붙여넣기 [현재 구현] ─┐
표 복사·CSV/엑셀 업로드 [후속]  ─┼→ 공통 주문 검수표 → 합산/가격마감 → 명세서
사진 OCR [보류 실험]            ─┘
```

- 모든 입력 채널은 **공통 검수표**로 수렴한다. OCR·파일 입력을 핵심 흐름과 결합하지 않고 입력 어댑터로 격리한다.
- 우선순위: ① 표 복사/CSV/엑셀(정확·저비용) ② 사진 OCR(보류 실험). 종이 발주표 거래처(1곳)에는 **엑셀/파일 제공 가능성을 먼저 확인**한다.
- OCR 실험 2종(각각 별도 게이트): (a) 거래처 발주표 사진 → 품목·규격·거래처·수량·단위 추출·합산 (b) 매입처 명세서 사진 → 품목·수량·매입단가·금액 추출 → 가격 마감 후보.
- 실험 통과 기준: 실제 사진 10~20장에서 추출 정확도와 시간 절감을 측정 → 낮은 신뢰도 결과가 사용자 확인 없이 반영되지 않는 UX 포함 시에만 채택.
- **개인정보 정책(§12)과 세트**: 원본 이미지 기본 영구 저장 금지.

## 9. 모바일/PC 화면 역할과 수정 UX 규칙

**유지 [현재 구현]:** 좌측 사이드바, 기존 화면·메뉴 이름, 반응형 웹 1벌, 실무적 색·밀도.

**역할 분담 [설계 승인]:**
- 모바일(아침 현장): 발주 붙여넣기·검수·수량 확인 — 한 열 카드/목록, 큰 터치 영역, 핵심 필드 우선, 가로 넘침 금지.
- PC(낮 사무): 가격 마감·명세서·합산 — 조밀한 표, 키보드(Enter 이동·일괄 적용) 효율.

**현재 모바일 결함(수정 대상 기록) [현재 구현의 버그]:** 상단 메뉴 가로 넘침 · 대시보드 제목 줄바꿈 · 계정/로그아웃 표시 충돌. (앱 코드는 이번 세션에서 수정하지 않음 — 후속 UX 단계에서 처리)

**전 화면 수정 UX 규칙 [설계 승인]:** 업무 화면 안 인라인 수정(기준정보 화면 왕복 금지) · 검색 후 선택 · Enter 다음 칸 · 선택 행 일괄 변경 · 변경값 강조 · 저장 중/완료/실패 상태 · 임시 작업 자동 저장 또는 이탈 경고 · 파괴적 행동(최종 확정·취소·삭제)은 시각 구분. 카드 남발·중첩 카드·마케팅형 히어로 금지.

**벤치마크 원칙(기능 복제 금지):** MarketMan·inFlow·Sortly류 현장 운영 도구에서 다음 원칙만 차용 — 모바일은 현장 행동 먼저 / PC는 조회·가격·문서에 밀도 / 검색·예외 수정이 빠름 / 오늘 할 일과 미완료가 명확. (이번 세션은 외부 화면 열람 없이 원칙 수준만 기록 — 구체 화면 참고가 필요해지면 공식 공개 화면만, 출처 URL과 관찰·추론 구분 원칙으로 별도 조사)

## 10. 승인된 대시보드 구조 [설계 승인·미구현]

```text
7월 11일 오늘 업무                          미처리 N건

[새 발주 N] [매입처 발주 N] [가격 대기 N] [명세서 준비 N]

지금 먼저 할 일
- 가람식당 · 품목 6개 · 단위 확인 1        [열기]
- 매입처 2곳 · 발주 준비                    [합산표]
- 오늘 매입명세서 N건 · 판매가 마감 필요   [가격 마감]
```

- 대시보드는 진행판이 아니라 **실제 주문 상태의 읽기 전용 집계 큐**다. 별도 상태를 저장하지 않는다.
- 기존 사이드바·다른 화면은 유지. 모바일은 같은 정보를 한 열로.
- "가격 대기" 카드는 경로 B 구현 전까지 0건/숨김 — 대시보드 개편을 상태 모델보다 먼저 출시하지 않는다(§13 순서).

## 11. 데이터 모델 대안 비교와 권장안 [개념 설계 — SQL 없음, 구현 승인 아님]

**대안 1 — 기존 `ordermoa_orders` 상태 모델 활용/확장:** 현재 CHECK에 이미 있는 `draft`를 가격 대기 의미로 재사용할지, 의미가 더 분명한 `quantity_confirmed`를 추가할지 R1에서 비교한다. 판매가 미확정 표현도 `unit_price` null 허용, 별도 `priced_at`/가격 상태 필드 등으로 비교하고 마감 시 단가를 스냅샷으로 고정한다. 0원은 실제 판매가일 수도 있으므로 `0=미확정`으로 겸용하지 않는다.

**대안 2 — 별도 초안 객체:** 가격 대기 주문을 새 테이블(예: `ordermoa_order_drafts`+lines)에 저장, 최종 확정 시 기존 orders/order_items 생성.

| 기준 | 대안 1(orders 단일 소스) | 대안 2(별도 초안) |
|---|---|---|
| 기존 확정 주문 호환 | 기존 행 무변경(confirmed=최종 확정으로 해석). CHECK 확장 필요 | 기존 테이블 완전 불변(가장 보수적) |
| unit_price 스냅샷 안전 | 마감 전 미확정을 명시적으로 표현해야 함(null vs 별도 상태/시각 비교). `0=미확정` 겸용 금지. 최종 확정 뒤 불변을 앱+DB로 보호 | orders에는 확정값만 들어옴(원칙 그대로) — 초안 쪽은 자유 수정 |
| 가격 없이 합산 | 같은 테이블이라 합산 쿼리 단순(상태 in 필터) | 합산이 두 소스(초안+확정) 병합 — 쿼리·화면 복잡 |
| 매입처 발주 추적 | 상태/화면 파생으로 시작 가능 | 동일 |
| 재시도·부분 실패 복구 | 마감=update라 단순 | 확정=초안→orders 복사라 부분 실패 보상 필요(현 saveOrder 보상 패턴 재사용 가능) |
| RLS·company_id·교차회사 | 기존 정책·트리거 재사용 | 새 테이블에 RLS 4정책+트리거 추가 필요 |
| 쿼리·화면 복잡도 | 낮음(orders 단일 소스) | 높음(이중 소스, id 승계 문제) |
| additive/idempotent 마이그레이션 | 기존 draft 재사용 시 CHECK 변경은 피할 수 있음. 신규 상태/가격 필드 또는 unit_price nullable 중 선택에 따라 위험이 달라짐 | 테이블 추가만(가장 additive) |
| 기존 데이터 backfill | 불필요(confirmed 그대로) | 불필요 |

**권장안: 대안 1(기존 orders 단일 소스 유지).** 근거: 합산표·주문 목록·월합계가 전부 orders 단일 소스를 전제하며(코드 확인), 이중 소스는 조회 화면 전반의 복잡도를 키운다. 단, 내부 표현은 아직 미확정이다. R1에서 `draft 재사용 vs 신규 상태`, `unit_price nullable vs 별도 가격 상태/시각`을 각각 비교한다. 스냅샷 안전은 "가격 대기 상태에서만 단가 수정 가능, 최종 확정 후 update 차단"을 앱+DB(정책/트리거는 마이그레이션 설계 세션에서 결정)로 이중 보호한다. nullable 후보를 택하면 generated amount와 기존 조회가 null을 어떻게 다루는지 실측한다. **이 권장은 구현 승인이 아니다**(§15).

## 12. 보안·개인정보·원본 이미지 정책

- 매입처 명세서·발주표 사진에는 상호·전화·사업자번호가 포함될 수 있다 → **민감정보 취급**.
- 원본 이미지 기본 영구 저장 금지. (향후 OCR 실험 시) 업로드→임시 처리→즉시 삭제, 추출 결과만 사용자 검수 후 반영, 낮은 신뢰도 자동 반영 차단.
- 저장소에 원본 사진·실사업자 엑셀 커밋 금지(기존 W20 원칙 유지, .gitignore 안전망 유지).
- raw_text 삭제 가능 원칙(헌장 §3.5), service role key 클라이언트 금지, `ordermoa_` 접두사·RLS 4정책·교차회사 트리거 등 기존 보안 불변 규칙 전부 유지.

## 15. 열린 결정과 Codex 승인 게이트

문서 개편·아키텍처 비교가 끝난 뒤에도 아래는 **별도 승인 전 착수 금지**:

1. 가격 대기 상태의 실제 DB 모델(대안 1 채택 여부, 기존 `draft` 재사용 vs 신규 상태, `unit_price` nullable vs 별도 가격 상태/시각) — R1 게이트
2. 최종 확정 전 라인 수정 방식(update 범위)과 정정 절차 설계
3. 실제 매입가 저장 범위(§6 권장 b의 채택)
4. 가격 마감 화면의 제안 규칙 세부(최근 최종 판매가 조회 범위 등)
5. 거래처별 해석 기억 스키마
6. OCR 처리 방식·외부 서비스·원본 보관 정책
7. 대시보드 외 기존 화면의 구체 UI 변경 범위
8. 가격 대기 주문의 "워터마크 미리보기" 허용 여부(§5)

> 본 문서와 기준서가 충돌하면 기준서(사용자 승인)가 우선하고, 구현 완료 여부 판단은 코드·테스트·마이그레이션·실측 증거를 따른다.
