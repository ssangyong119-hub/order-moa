# 오더모아 시스템 메타 프롬프트 (전체 개발 헌장)

작성일: 2026-07-07
작성 주체: Claude 초안, Codex 검수 반영
관련 문서: `docs/order-moa-expanded-roadmap.md`(단계별 로드맵), `docs/order-moa-module-map.md`(모듈 맵), `docs/order-moa-ai-working-rules.md`(AI 작업 규칙)

## 1. 제품 정체성

### 1.1 오더모아는 누구를 위한 앱인가

- **도소매/식당납품 중간 납품업자 사장님.** 매일 아침 카카오톡·문자로 여러 식당·마트에서 발주가 들어오고, 이를 수기로 옮겨 적어 매입처에 발주하고, 배송 후 거래명세서를 끊는 사람.
- 비개발자이며, 엑셀·이카운트가 익숙하지만 "발주 문자를 장부로 옮기는 반복 작업"에 하루 1~2시간을 쓴다.
- 오더모아의 강점은 단 하나다: **"카톡/문자 발주를 빠르게 정리해서 매출 주문과 매입처 발주로 연결"**.

### 1.2 오더모아가 하지 않는 것

| 하지 않는 것 | 이유 |
|---|---|
| 이카운트 전체 대체 | 회계/세무/재고 전체를 흉내 내면 어느 것도 못 이긴다. 오더모아는 이카운트 **앞단**(발주 수집~명세서)에 산다 |
| 세무 기장·부가세 신고 | 세무사의 영역. 근거 데이터만 보존한다 |
| 완전 자동화(OCR·카톡 자동 읽기) | 정확도·정책 리스크. 사람이 확인하는 반자동이 원칙 |
| 범용 재고 ERP | 납품업 특화 흐름이 먼저. 재고는 3차에서 좁게만 |

### 1.3 왜 좁게 시작하는가

- 수요 근거 설문이 **5건**뿐이다. 큰 기능은 검증 없이 만들면 전부 추측이 된다.
- 좁은 MVP(붙여넣기→파싱→합산표→발주 문장→명세서)는 사장님 1명만 써도 가치가 검증된다.
- 1차가 좁아야 2차/3차가 안전하다: 확정 주문 데이터가 올바르게 쌓이면 미수금·세금계산서·리포트는 전부 그 위에 얹는 조회 기능이다.

## 2. 핵심 업무 흐름

### 2.1 모바일 (아침, 발주 수집)

```
카톡/문자에서 발주 원문 복사
  → 오더모아 열고 거래처 선택 + 붙여넣기
  → 파싱 결과 확인 (미매칭/수량불확실/후보확인은 빨강·노랑으로 막힘)
  → 품목 검색·신규 품목 즉석 등록·단가 즉석 저장으로 그 자리에서 해결
  → 주문 확정 (orders + order_items 저장, 단가는 확정 시점 스냅샷)
```

### 2.2 PC (낮, 발주·서류)

```
품목별 합산표 (여러 거래처 주문을 품목별 총수량으로)
  → 보낼 품목 체크 → 매입처별 발주 문장 생성·복사 → 카톡으로 매입처에 전송
  → 주문 목록 / 거래처별 조회
  → 거래명세서 미리보기 → 브라우저 인쇄
```

- 확정 차단 규칙은 파서의 헌법이다: **미매칭·수량 불확실·다중 후보 미확인 라인이 하나라도 남으면 확정 불가** (`canConfirm`). 시스템은 후보만 제안하고 확정은 항상 사람이 한다.
- 파싱은 순수 함수(`order-parser.ts`)로 유지한다. UI·저장소와 절대 섞지 않는다.

## 3. 데이터 보존 원칙 (불변 규칙)

이 절의 규칙은 차수와 무관하게 **영구 불변**이다. 위반하는 코드는 리뷰에서 반려한다.

1. **주문 확정 시 `거래처·일자·품목·수량·단가·라인금액`은 반드시 보존한다.** 이것이 거래명세서 재출력·기간 집계·세금계산서 대조의 근거다.
2. **`order_items.unit_price`는 확정 시점 스냅샷이다.** 과거 명세서를 만들 때 `customer_prices`를 재조회하면 안 된다. 단가를 바꿔도 과거 주문 금액은 변하지 않는다.
3. **`order_items.amount`는 DB generated 컬럼**(`round(quantity × unit_price)`)이다. insert payload에 절대 포함하지 않는다. 합계는 라인 amount의 합이며 합산 후 반올림하지 않는다.
4. **예상 마진은 저장하지 않는다.** 표시 시점에 `products.base_purchase_price`로 계산하는 참고값이다. "예상 마진은 참고값이며 실제 정산과 다를 수 있습니다" 문구를 유지한다. 정확 회계 마진은 2차 이후 별도 모델.
5. **`raw_text`(발주 원문)는 삭제 가능해야 한다.** 삭제 시 확정 주문은 유지되고 raw_text만 null이 된다. 그래서 `order_imports`와 `orders`는 FK로 묶지 않는다.
6. **세금계산서 직접 발행은 후순위지만 근거 데이터(거래처별 기간 금액)는 1차부터 보존한다.** `orders.order_date + customer_id + Σ order_items.amount` 쿼리로 언제든 산출 가능해야 한다.
7. **삭제는 soft delete 우선.** customers/products는 `archived_at`, orders는 `status='cancelled'`. orders에는 delete 정책 자체가 없다.
8. **금액은 KRW integer, 수량은 numeric.** 부동소수점 금액 금지.

## 6. DB / 보안 방향

### 6.1 기본 구조 (적용 완료)

- Supabase(PostgreSQL + Auth). **공유 프로젝트(yangsan-inventory)** 위에 살기 때문에 모든 객체는 `ordermoa_` 접두사 필수 — 테이블·함수·트리거·정책 전부.
- 9개 테이블: companies, company_members, customers, products, product_aliases, customer_prices, order_imports, orders, order_items.
- 회사 격리 3중 방어: ① **RLS**(`ordermoa_is_company_member()` security definer 헬퍼, 전 테이블) ② **교차 회사 FK 트리거**(참조 행의 company_id 일치 강제) ③ 앱 레벨 스코프 쿼리. 실측 완료: A/B 격리 0/0/0, 위조 insert 42501 차단.
- 회사 생성은 `ordermoa_create_company_with_owner()` RPC(security definer)로 companies+owner 멤버를 원자 처리. anon 실행 불가.

### 6.2 보안 불변 규칙

- **service role key는 클라이언트에 절대 노출 금지**(서버 전용). `.env.local`은 미추적 유지, 커밋 금지.
- 비로그인(anon)은 전 테이블 접근 불가. "화면에서 숨김"을 권한 처리로 치지 않는다 — 권한은 항상 DB(RLS)에서 강제.
- 새 테이블 추가 시 반드시: `company_id NOT NULL` + RLS 4정책 + (참조가 있으면) 교차 회사 트리거 + `ordermoa_` 접두사. 하나라도 빠지면 마이그레이션 반려.
- 원본 사업자 데이터(태백식품 엑셀 등)는 커밋 금지, 가명화만 사용. 샘플 데이터에 실거래처명·전화·사업자번호 금지.

### 6.3 회사/사용자/권한

- 1차: owner 단독. `company_members.role`에 staff 여지는 이미 있음. staff UI·세분 권한은 2차.

### 6.4 매입처 테이블 검토 (현재 최대 스키마 쟁점)

현재 `purchaseSupplierId/Name`은 **앱 화면 상태와 샘플 데이터에만 존재**하고 DB에는 컬럼도 테이블도 없다. 신규 품목 즉석 등록의 "기본 매입처"도 DB에 저장되지 않는다(화면 상태만). 방치하면 새로고침 시 매입처 지정이 사라지는 반쪽 기능이 된다.

권장안(1차 보강, 8c 전 권장, additive 마이그레이션):

```
ordermoa_suppliers (id, company_id, name, memo, created_at, archived_at)
ordermoa_products.purchase_supplier_id uuid nullable FK → suppliers
```

- RLS 4정책 + 교차 회사 트리거 + unique(company_id, name) 포함.
- 원가/발주이력/미지급은 2차에서 suppliers 위에 얹는다.
- 마이그레이션 작성·적용은 Codex 승인 후.

## 7. 테스트 / 검증 원칙

**검증 한 세트** — 코드 변경이 있는 모든 작업 후 실행하고 결과를 보고에 남긴다:

| 검증 | 명령/방법 | 통과 기준 |
|---|---|---|
| 루트 회귀 | `npm test` (루트) | 전건 통과 (현재 5/5) |
| web 단위 | `cd web && npm test` | 전건 통과 (현재 78/78) — 파서 fixture 포함 |
| 빌드 | `cd web && npm run build` | 성공 |
| 보안 감사 | `npm audit --audit-level=low` | 0건 |
| 브라우저 smoke | dev 서버 응답 + 핵심 흐름 클릭 | 붙여넣기→확정→합산표 동작 |
| 모바일 | 390px 뷰포트 | 아침 흐름 레이아웃 유지 |
| 인쇄 | 거래명세서 → 브라우저 인쇄 미리보기 | 표 형태 유지, 빈 행 패딩 |
| RLS | A/B 회사 격리 시나리오 | 타사 select 0행, 위조 insert 42501 |

- 새 로직은 **순수 함수로 분리해 단위 테스트 우선**(파서·합산·저장 payload 빌더가 선례). UI에 로직을 심으면 테스트 불가로 반려.
- 파서 변경 시 실제 발주 fixture(`order-moa-real-order-test-*`)를 갱신·통과시킨다.
- UI 버그는 로직 통과만으로 완료 선언 금지 — 화면 확인(스크린샷/getComputedStyle)까지가 검증이다.
- 디버깅과 리뷰는 한 세트: 원인→수정→검증 결과를 worklog에 기록한다.
- `.env.local`을 검증 목적으로 옮겼으면 반드시 원위치 복원 후 git 미추적 재확인.

## 8. AI 작업 방식

상세 규칙은 `docs/order-moa-ai-working-rules.md`. 핵심만:

1. **작업 전**: `git status` 확인(기존 미커밋 변경을 건드리지 않는다) → 관련 문서·코드 읽기 → 진행현황 JSON으로 현재 위치 파악.
2. **구현 중**: 좁은 MVP 우선, 기능 확장은 1차/1.5차/2차/3차 딱지를 먼저 붙이고 시작. 순수 함수 분리, 기존 패턴 재사용.
3. **작업 후**: 검증 한 세트(§7) → `docs/agent-worklog.md` 기록 → 진행현황 JSON 갱신(필요 시 HTML/XLSX 재생성).
4. **커밋/머지/push는 하지 않는다** — Codex 판단. Claude는 보고만.
5. **보고 형식**: 사용자는 비개발자다. 변경 요약(쉬운 말) + 검증 결과 + **[개선 아이디어] / [위험] / [나중]** 3분류를 항상 포함.
6. 민감정보(키·원본 사업자 데이터·전화번호)는 출력·커밋·로그 금지.

## 9. 장기 기능 아이디어 (백로그 — 약속 아님)

우선순위·위험도는 `docs/order-moa-expanded-roadmap.md`에서 관리한다. 여기 있다고 만드는 것이 아니다.

- **매입처 축**: 매입처 관리 → 매입처별 원가 이력 → 발주 이력 저장 → 미지급 관리 → 발주 추이 리포트
- **자금 축**: 미수금 수동 체크 → 입금 기록 → 오래된 미수금 알림 → 지불/미지급 통합
- **재고 축(좁게)**: 입출고 수량 기록 → 창고 이동 → 반품/취소 반영 (재고 평가는 하지 않는다)
- **서류 축**: 명세서 양식 개선 → 저장형 명세서+채번 → PDF 파일 → 2부 출력 → 세금계산서 근거 정리 → 마감
- **리포트 축**: 거래처별 월/년 매출 → 품목별 판매 추이 → 매입처별 발주 추이 → 대시보드
- **운영 축**: 직원 권한 → 백업/내보내기 → 엑셀 업로드/다운로드 → 모바일 최적화
- **후순위/제외 재확인**: OCR·카톡 자동 읽기·이카운트 연동·홈택스 직접 발행·은행 자동 매칭은 명시적 검증 없이는 착수하지 않는다.

## 10. Claude 관점의 개선 제안 TOP 10

| # | 제안 | 왜 |
|---|---|---|
| 1 | 매입처를 DB로 승격(§6.4) | 지금 유일하게 "저장 안 되는 척하는" 기능. 즉석 등록의 기본 매입처가 새로고침에 증발 |
| 2 | `page.tsx` 뷰 단위 분리 | 1,433줄. 기준정보 3화면 추가 전이 마지막 분리 기회 |
| 3 | 기준정보 CRUD를 "발주 흐름의 부속"으로 설계 | 별도 관리자 화면보다 "파싱하다 막힌 것을 고치러 가는 화면"이 실사용에 맞음 — 즉석 등록과 같은 빌더 재사용 |
| 4 | 주문 저장 RPC 원자화 | 현재 orders→items 2단 insert + cancelled 보상. RPC 트랜잭션이면 보상 코드 자체가 사라짐 |
| 5 | `ordermoa_customers`/`products`에 unique(company_id, name) 검토 | 시드 멱등이 이름 기준인데 DB가 이름 중복을 허용 — 동시 실행 중복 생성 구멍 |
| 6 | 파싱 fixture를 회귀 게이트로 승격 | 실제 발주 fixture가 이미 있음. 파서 변경 시 자동 필수 통과 목록으로 |
| 7 | 진행현황 HTML/XLSX 재생성 스크립트를 리포에 포함 | 지금은 세션 스크래치패드에 있어 유실됨. `scripts/`에 두면 누구나 JSON만 고치면 됨 |
| 8 | raw_text 저장을 8c에 묶기 | order_imports 테이블은 이미 있는데 앱이 안 씀. 파싱 검수·분쟁 대응의 근거 |
| 9 | 명세서 양식을 spec 문서 기준으로 정돈 | `delivery-note-print-spec.md`가 이미 있음. 코드가 spec을 따라가는지 체크리스트화 |
| 10 | 데모 모드↔DB 모드 차이를 화면에 명시 | "데모 모드 · 저장 안 됨" 표시는 있으나, 손님에게 보여줄 때 혼동 여지 — 데모에서 확정 시 안내 배너 |
